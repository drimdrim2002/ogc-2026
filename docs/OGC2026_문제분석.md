# Optimization Grand Challenge 2026 (OGC 2026) 문제 분석
### "The Grand Shipyard Puzzle: Pack the Block, Beat the Clock" — 상세 분석 보고서

> 원문: OGC 2026 Organizing Committee, 2026-06-15 (Document Version 1.2)
> 문서 갱신 사항: 공식 웹사이트를 최신 버전의 기준으로 보아야 하며, 참가자는 업데이트를 직접 확인할 책임이 있다. 중요한 변경 사항은 공식 웹사이트에 공지된다.

---

## 1. 대회 개요

OGC 2026은 **조선소의 블록 배치 및 스케줄링 문제**를 다루는 최적화 경진대회다. 문제의 본질은 세 가지 하위 문제가 동시에 얽혀 있다는 점이다.

| 하위 문제 | 설명 |
|---|---|
| **배정(Assignment)** | 각 블록을 어느 베이에 배치할지 |
| **패킹/배치(Packing/Layout)** | 베이 내부의 어느 위치와 어떤 방향으로 놓을지 |
| **스케줄링(Scheduling)** | 언제 반입(ENTRY)하고 언제 반출(EXIT)할지 |

**분석:** 즉, 이 문제는 **2D/3D 비정형 도형에 대한 컷팅스톡/패킹 문제 + 병렬 기계 스케줄링 문제 + 자원(공간) 제약을 동시에 푸는 복합 조합최적화 문제**로 요약할 수 있다. 세 요소는 서로 독립적이지 않고 상호작용한다. 예를 들어 베이가 가득 차면 ENTRY가 지연되고, 이는 납기 지연으로 이어질 수 있으므로 난이도가 매우 높다.

## 2. 문제 정의 (Section 1)

### 2.1 핵심 용어

| 기호 | 용어 | 정의 |
|---|---|---|
| $M=\{1,...,m\}$ | 베이(Bay) | 크기 $W_j \times H_j$의 고정 작업 공간 |
| $N=\{1,...,n\}$ | 블록(Block) | $K_i$개의 다각형 레이어로 구성되고 $O_i$개의 방향 옵션을 갖는 3D 구조물 |
| $R_i$ | 릴리즈 시점 | 블록 $i$가 처리를 시작할 수 있는 가장 이른 시점 |
| $D_i$ | 납기일 | 블록 $i$의 목표 완료 시점 |
| $P_i$ | 처리시간 | 블록 $i$를 처리하는 데 필요한 시간 |
| $ENTRY_i$ | 반입 시점 | 블록이 베이에 배치되는 시점 |
| $EXIT_i$ | 반출 시점 | 블록이 베이에서 나가는 시점 |
| $T_i$ | 지연시간 | $T_i = \max(0, EXIT_i - D_i)$ |
| $L_i$ | 작업량(Workload) | 블록 처리에 필요한 총 작업량 |
| $S_{ij}$ | 선호도(Preference) | 블록 $i$가 베이 $j$에 배정되는 것을 얼마나 선호하는지를 나타내는 점수 |

### 2.2 문제 설정 요약

- 하나의 베이는 **여러 블록을 동시에** 수용할 수 있다. 단, 블록들이 공간적으로 겹치지 않아야 한다.
- 각 블록은 고유한 $R_i, P_i, D_i$를 가지므로, 실행 가능한 해를 얻으려면 **공간 배치와 시간 스케줄링을 동시에 고려**해야 한다.

### 2.3 베이 구조와 크레인 운영 규칙 (매우 중요한 세부사항)

- 각 베이는 **독립적인 크레인**을 가지므로, 서로 다른 베이의 작업은 간섭하지 않는다.
- 크레인 작업 목록은 **일(day) 단위**로 주어지며, 하루에 **여러 개의 작업(ENTRY/EXIT)** 을 수행할 수 있다. 작업 횟수 제한은 없다.
- **같은 날에는 모든 EXIT 작업이 모든 ENTRY 작업보다 먼저 수행되어야 한다.**
  - **구현 참고(checker 동작, PDF 본문 아님):** 같은 타입 작업끼리의 순서는 알고리즘이 정하지만, `utils.py`에서는 이 리스트 순서가 의미를 가진다. Stage 5는 한 시점의 작업들을 리스트 순서대로 live present-set에 대해 순차적으로 재생한다. 같은 날 두 EXIT가 있고 한 블록이 다른 블록의 인양 경로를 막는다면, 막고 있는 블록(위에 걸쳐 있거나 overhang인 블록)의 EXIT를 먼저 나열해야 한다. 같은 날 ENTRY의 경우 Stage 2가 같은 시점에 들어오는 모든 블록을 이미 존재하는 것으로 간주하므로(`entry_k <= t < exit_k`), 같은 날 들어오는 블록 중 어느 하나가 다른 하나를 막는다면 어떤 나열 순서에서도 해는 infeasible이다.
- 예: 처리시간이 3이고 day 5에 ENTRY한다면, EXIT는 가장 빨라도 **day 8**에만 가능하다. 처리는 day 5, 6, 7에 이루어지므로 $EXIT_i - ENTRY_i \ge P_i$이다.
- 블록은 **베이에 놓여 있는 반개구간 [ENTRY, EXIT) 동안 공간을 점유**한다. 반개구간이라는 점에 유의해야 한다.

### 2.4 블록 구조

- 각 블록은 $K_i$개의 **다각형 레이어**로 이루어진 3D 구조물이며, 레이어는 비볼록일 수 있다. 모든 레이어의 높이는 동일하다고 가정한다.
- "빈 레이어"는 없고, 인접한 레이어들은 항상 물리적으로 붙어 있어야 한다. 즉 "떠 있는" 레이어는 허용되지 않는다.
- 각 블록에는 **미리 정해진 개수의 방향 옵션 $O_i$** 이 주어진다. 자유 회전이 아니라 이산적인 후보 방향 중 하나를 선택하는 방식이다.
- 각 블록은 $L_i$(작업량)와 $S_{ij}$(베이별 선호도 점수)를 가진다.
  - $L_i$는 베이 간 작업량 불균형을 최소화하는 목적함수($Z_2$)에 사용된다.
  - $S_{ij}$는 선호도를 최적화하는 목적함수($Z_3$)에 사용된다.

### 2.5 결정 변수 (Section 1.5)

각 블록 $i$에 대해 다음 네 가지를 결정해야 한다.
1. 배정할 베이 $j$
2. 베이 내부 위치 $(x, y)$
3. 선택할 방향
4. $ENTRY_i$, $EXIT_i$

### 2.6 제약 조건 (Section 1.6)

#### (1) 배정 제약
- **모든 블록은 정확히 하나의 베이에 배정**되어야 한다. 미배정 블록은 허용되지 않는다.
- 모든 블록은 **정확히 하나의 ENTRY와 하나의 EXIT** 작업을 가진다. **한번 배치된 블록은 이동하거나 회전할 수 없다.** 재배치는 허용되지 않는다.

#### (2) 시간 제약
- **릴리즈 제약**: $ENTRY_i \ge R_i$
- **처리시간 제약**: $EXIT_i - ENTRY_i \ge P_i$
- 참고: 보통 $D_i - R_i > P_i$가 성립하므로, 스케줄링에는 "슬랙"이 있다. 이 슬랙이 다른 블록과 조율할 여지를 만든다.
- $EXIT_i > D_i$이면 지연(tardiness)이 발생한다.

#### (3) 공간 제약 — 가장 복잡한 부분
- **충돌 정의**: 같은 레벨에 있는 두 블록 레이어의 **내부(interior)** 가 겹치면 충돌이다. 하지만 **경계(edge)를 공유하는 것은 충돌로 보지 않는다.** 접촉은 허용된다.
  $$C(\cdot) = \begin{cases}0 & \text{if } int(\cdot)\cap int(\cdot)=\emptyset\\1 & \text{otherwise}\end{cases}$$
- $N(t,j)$ := 시점 $t$에 베이 $j$에 실제로 존재하는 블록 집합($ENTRY_i \le t < EXIT_i$).

| 제약명 | 설명 |
|---|---|
| **베이 포함 제약** | 블록은 배정된 베이의 경계 안에 완전히 들어가야 한다 |
| **레이어 충돌 회피 제약** | 같은 시점에 같은 베이에 있는 두 블록은 **같은 레벨의 레이어끼리** 충돌이 없어야 한다. 검사는 레벨 $l=1,...,\min(K_{i1},K_{i2})$까지 수행된다. 흥미로운 점은 **위에서 본 평면도(top view)에서는 겹쳐 보이더라도**, 실제 같은 레이어 레벨에서 겹치지 않으면 문제가 없다는 것이다. Figure 7(a)는 서로 다른 계단식 레이어에서만 만나는 경우를 보여준다 |
| **크레인 작업 제약** | 블록을 반입/반출할 때, 즉 수직으로 이동시킬 때, 해당 블록의 레이어는 **같거나 더 높은 레벨**에 있는 다른 블록의 레이어와 충돌해서는 안 된다. 이는 크레인의 실제 물리를 반영한다. 위에서 수직으로 내리거나 들어 올릴 때 다른 블록에 걸리면 안 된다는 의미다 |

> **분석 / 핵심 통찰:** 공간 제약은 단순한 2D bin-packing 문제가 아니라, **레이어별(높이별) 겹침을 허용하는 준 3D 패킹 문제**다. 두 블록이 top view에서 겹쳐 보여도 서로 다른 레이어에서만 만나면 정적인 배치로는 괜찮다(레이어 충돌 회피). 하지만 크레인으로 넣고 뺄 때는 "수직 통로"가 막히면 안 된다(크레인 제약). 따라서 이 두 조건은 별도로 검사해야 한다.

### 2.7 목적함수 (Section 1.7)

세 가지 목적을 가중합하여 최소화한다.

$$\min\; w_1 Z_1 + w_2 Z_2 + w_3 Z_3$$

| 항 | 이름 | 수식 | 의미 |
|---|---|---|---|
| $Z_1$ | 총 지연시간 | $\sum_i T_i$ | 납기 준수 성능 |
| $Z_2$ | 작업량 불균형 | $\displaystyle\left\lfloor\max_{j_1 \neq j_2}\Big\vert u_{j_1}\sum_{i\in N(j_1)}L_i - u_{j_2}\sum_{i\in N(j_2)}L_i\Big\vert\right\rceil$ | 베이 간 정규화된 작업량의 최대 편차. 베이 면적에 따른 $u_j$로 가중된다. PDF에는 최대 불균형 식 주위에 floor/rounding 형태의 구분자가 붙어 표시되어 있다. |
| $Z_3$ | 선호도 손실 | $\sum_{j}\sum_{i\in N(j)} (S_i^{max} - S_{ij})$ | 각 블록의 최선호 베이 대비 손실 총합. 모든 블록이 최선호 베이에 배정되면 $Z_3=0$ |

- $u_j = \dfrac{\text{전체 베이 평균 면적}}{W_j \times H_j}$ → **베이가 클수록 가중치가 작아진다.** 이는 큰 베이에 작업량이 집중되어도 혼잡도가 상대적으로 낮다는 생각을 반영한다.
- 가중치 $w_1, w_2, w_3$는 인스턴스 JSON 안에 제공된다. 예: $w_1=26667, w_2=10, w_3=300$.
  - **분석:** 예시에서는 가중치 간 스케일 차이가 매우 크므로, 실제로는 지연시간이 지배적인 목적이 될 수 있다. 단, 우선순위는 인스턴스별로 확인해야 한다.

## 3. 문제 인스턴스 정의 (Section 2, JSON 형식)

인스턴스 JSON은 4개의 최상위 키로 구성된다.

```
{
  "name": "...",
  "bays": [ {width, height}, ... ],
  "blocks": [ {release_time, due_date, processing_time, workload,
               bay_preferences, shape}, ... ],
  "weights": {"w1":..., "w2":..., "w3":...}
}
```

### 주요 규칙 및 함정

- **인덱싱**: 인스턴스/솔루션 파일은 **0-based** 인덱싱을 사용한다. 반면 Section 1의 수식 정의는 1-based 인덱싱을 사용하므로 구현 시 혼동에 주의해야 한다.
- 훈련 인스턴스는 실제 조선 환경을 모사하도록 생성되며, 많은 블록 수나 빡빡한 릴리즈/납기 일정 등 다양한 난점을 포함한다. 따라서 알고리즘은 특정 패턴에 과적합하기보다 서로 다른 운영 조건에 일반화되어야 한다.
- `bay_preferences`: 각 블록에 대해 각 베이의 선호도 점수를 담은 리스트다. **한 블록의 선호도 점수 합은 항상 100으로 정규화**되어 있다.
- 모든 시간값과 선호도값은 **정수**다.
- `shape`: 방향별 딕셔너리 리스트다. 각 방향은 `orientation`(정수 ID)과 `layers`(레이어별 다각형 정점 리스트)를 가진다. `layers`는 **가장 낮은 레이어부터 가장 높은 레이어 순서**로 정렬된다.
  - **기준점(reference point)**: 레이어 0의 **첫 번째 정점은 항상 (0.0, 0.0)** 이다. 이것이 기준점이며, 나머지 정점들은 이 기준점에 대한 상대 좌표로 표현된다.
  - 블록 위치 $(x,y)$를 지정하면 기준점이 $(x,y)$로 평행이동하고, 나머지 정점들은 상대 위치를 유지한다. 즉 **방향에 따라 기준점이 항상 좌하단에 오지는 않는다**(Fig. 8 참고).
  - 정점 좌표는 **최대 네 자리 유효숫자의 실수**일 수 있고, 이로 인해 수치 불안정성이 생길 수 있다. 따라서 최종 검증 단계에서는 **제공된 `utils.py`의 함수를 사용하는 것을 강력히 권장**한다. 평가 서버도 같은 함수를 사용한다.

## 4. 솔루션 제출 형식

솔루션은 `{"operations": {date: [list of operations]}}` 형태의 딕셔너리다.

- 날짜 키(예: `"0"`, `"1"`, `"28"`)는 작업이 발생하는 날짜에 대해서만 명시하면 된다. 모든 날짜를 나열할 필요는 없다.
- 작업 타입: `"ENTRY"`는 block_id, bay_id, x, y, orient_idx가 필요하고, `"EXIT"`는 block_id, bay_id만 필요하다.
- **같은 날짜 안에서는 모든 EXIT 작업이 모든 ENTRY 작업보다 먼저** 나열되어야 한다. 이는 앞서 설명한 제약의 재확인이다.
- 솔루션 예시의 모든 숫자값은 정수여야 하며, **특히 x와 y는 소수일 수 없다**. 평가 시스템은 위치값을 반올림한 뒤 `utils.check_feasibility()`로 가능성을 검사한다.

### 5.2 제출 승인 흐름

- 유효하지 않은 제출은 평가 전에 거절된다. 승인된 제출은 예비 **sanity check**를 통과한 것이지만, hidden problem에서의 성공 실행이나 정답성을 보장하지는 않는다.
- **가장 최근에 승인된 제출**이 평가와 리더보드 반영의 기준이 된다.
- 제출이 거절되면 회신에 간단한 거절 사유가 포함되며, 수정한 제출은 즉시 다시 제출할 수 있다.

### 5.3 평가 결과 상태 종류

| 상태 | 의미 |
|---|---|
| Feasible solution found | 성공, 목적값이 표시됨 |
| The solution returned is infeasible | `check_feasibility()` 실패 |
| Time limit exceeded | 시간 제한 초과. 제한값은 대회 종료 후 공개됨 |
| Algorithm raised an exception | 예외 발생. hidden instance 정보 보호를 위해 상세 내용은 공개되지 않음 |
| Algorithm process terminated unexpectedly | 비-Python 코드 실행 중 크래시 또는 강제 종료로 추정 |
| Tried to use unavailable Python package or function | import 에러 |

> 목적값은 솔루션이 **feasible**일 때만 표시된다.

### 5.4 평가 서버 사양 및 실행 제약

- 사양: **AMD Ryzen Threadripper PRO 9955WX**, Ubuntu 24.04 LTS
- 시간 제한: 문제별로 다르며, 일반적으로 몇 분에서 약 30분 정도로 예상된다. 정확한 제한은 대회 종료 후 공개된다. 시간 제한은 **wall-clock** 시간 기준으로 측정되므로, 알고리즘은 내부적으로 경과 시간을 모니터링해야 한다.
- 제한 시간 안에 솔루션을 반환하지 못하면 크래시/오작동 또는 시간 제한 초과로 처리된다.
- 리소스 제약:
  - 인터넷 접근 **불가**
  - 실행 폴더의 상위 디렉터리 접근 **불가**
  - CPU는 **최대 4코어(400%)** 로 제한
  - 메모리는 **최대 16GB** 로 제한
- `firejail`과 `cpulimit`로 강제되며, 이들과 충돌하는 코드는 금지된다.
- 실행 제약을 위반하면 실격될 수 있다.
- 개발 환경과 서버 환경 차이를 고려해 **절대경로보다 상대경로 사용을 권장**한다.

### 5.5 리더보드 점수 체계

문제당 점수:

$$\text{score} = \begin{cases} -1 & \text{infeasible / TLE / crash} \\ R - n_b & \text{feasible (}R\text{ = 평가된 팀 수, }n_b\text{ = 자신의 목적값보다 더 좋은 값을 찾은 팀 수)} \end{cases}$$

- 전체 순위는 **모든 문제의 점수를 합산**하여 결정된다.
- 리더보드는 **정확한 순위가 아니라 티어(예: top 10/20/30)** 만 표시한다. 정확한 순위는 각 단계가 끝난 뒤에만 공개된다.
- 리더보드 결과는 **매시간 집계**된다. 각 리더보드 빌드는 모든 문제에서 결과를 낸 알고리즘을 기준으로 한다.
- 제출은 **선착순 큐**를 통해 처리되므로, 제출 시각과 실행 완료 시각은 다를 수 있다.
- **최종 수상팀**은 리더보드 점수뿐 아니라 **기술보고서 + 발표**까지 포함한 종합 평가로 결정된다. 가중치는 조직위 재량이다.

### 6.3 베이스라인 알고리즘 (Greedy, EDD 규칙)

- **EDD(Earliest Due Date)** 규칙 기반이다. 납기가 가장 빠른 블록부터 순차적으로 배정한다.
- 배치 위치는 AABB(axis-aligned bounding box)의 **우하단 꼭짓점 후보** 중에서 선택한다.
- **1단계에서는 배치할 때 크레인 제약을 무시**한다. infeasibility가 발생하면 2단계에서 **해당 블록을 베이가 빌 때까지 뒤로 미루는 방식**으로 복구한다.
- **분석 / 구현 참고:** 이 베이스라인은 사실상 낮은 기준선에 가깝다. 따라서 **크레인 제약을 고려하면서 배치 순서와 위치를 최적화**하는 것이 실질적인 성능 개선 가능성이 큰 지점이다.

### 6.4 비-Python 언어 사용

- C/C++: **로컬 Ubuntu 24.04에서 컴파일**한 뒤 `.so`/실행 파일을 zip에 포함한다. 서버 측 컴파일은 없다.
- Java는 OpenJDK 17.0.18이 제공된다. .NET은 8.0.15가 제공된다.
- 비-Python 구현의 경우 필요한 바이너리/라이브러리를 zip에 포함하고 `myalgorithm.py`에서 호출해야 한다. 다른 팀에 영향을 주지 않도록 로컬화해야 하며, 서버 환경과의 호환성을 확인해야 한다. 이 모든 책임은 각 팀에 있다.

## 7. 대회 진행 방식 (Section 5)

```
예선(Preliminary) ──▶ 본선(Final) 진출팀 30-40개 선발
        │                        │
   자동 평가(리더보드)       자동 평가 + 기술보고서 + 발표
        │                        │
   티어별 표시              종합 심사로 최종 수상팀 결정
   (정확한 순위는 단계      (자동 점수 + 보고서 + 코드 +
    종료 후에만 공개)        발표 종합)
```

### 7.1 예선 단계
1. 자동 평가 → 티어 기반 리더보드 업데이트
2. 조직위의 **코드 검증** 병행 → 상위 30-40팀 본선 진출

### 7.2 본선 단계
1. 자동 평가(예선과 동일한 방식)
2. **기술보고서** 제출 필수. 코드와 보고서는 별도로 검토된다.
3. **발표** 필수
4. 자동 점수, 보고서, 코드, 발표를 종합하여 **최종 수상팀** 결정

### 7.3 평가, 공개, 윤리 (Section 5.3)

- 개별 평가 결과는 **공개되지 않는다**. 수상팀의 순위만 공개된다.
- 참가하려면 본선 진출팀의 코드와 기술보고서가 **공개**된다는 점에 동의해야 하며, 제출 코드는 **오픈소스 공개가 가능한 상태**여야 한다.
- 대회가 끝난 뒤에도 표절이나 제한 자원의 무단 사용 등 부정행위가 발견되면 **수상이 취소**될 수 있다.

## 9. 핵심 난이도와 전략적 시사점 요약 (분석)

1. **혼합 정수 비선형/조합 문제**: 배정 + 2D 비정형 도형 패킹(방향 선택 포함) + 시간 스케줄링이 동시에 결합되어 있다. 순수 MIP로 완전히 정식화하면 인스턴스 규모가 커질수록 Gurobi/Xpress도 제한 시간 안에 최적해를 찾기 어려울 가능성이 높다. **메타휴리스틱/휴리스틱 배치 + 국소 탐색 / 제약 완화 후 복구** 조합이 현실적인 접근으로 보인다.
2. **크레인 제약이 진짜 함정**: 단순히 "겹치지 않는다"만 확인해서는 부족하다. ENTRY/EXIT 순간에 **수직 통로가 막히는지**를 별도로 검증해야 한다. 베이스라인도 1단계에서 이를 무시하고 사후 복구하는 접근을 취한다. 처음부터 이를 고려한 배치 순서, 예를 들어 나중에 빼야 할 블록을 안쪽에 스택처럼 넣지 않는 구조를 설계하는 것이 핵심 개선 포인트다.
3. **목적함수 가중치의 스케일 불균형**: 예시 가중치($w_1=26667$ vs $w_2=10$, $w_3=300$)를 보면 $Z_1$(총 지연시간) 값 자체가 작더라도 가중치가 매우 크다. 따라서 **납기 준수가 사실상 지배적인 목적**이 될 가능성이 높다. 인스턴스별 가중치를 확인해 우선순위를 조정해야 한다.
4. **레이어 기반 충돌 판정의 이점 활용**: "top view에서 겹쳐도 실제 레이어 레벨이 다르면 괜찮다"는 규칙(Fig. 7(a))은 블록을 **계단식/맞물림 형태로 배치해 공간 효율을 크게 높일 수 있는 여지**를 뜻한다. 이는 단순 직사각형 패킹보다 높은 공간 활용률을 얻을 수 있는 지점이다.
5. **수치 안정성**: 정점 좌표가 최대 네 자리 유효숫자의 실수이므로 부동소수점 오차로 거짓 충돌이나 거짓 통과가 발생할 수 있다. 제공된 `utils.py`(Shapely 기반으로 추정)의 판정 함수를 그대로 재사용해 평가 서버와 동일한 기준으로 검증하는 것이 필수적이다.
6. **제출 운영 리스크 관리**: 12시간 쿨다운은 "승인된" 제출을 기준으로 하므로, zip 구조, 경로, 크기 등 거절 원인을 사전에 로컬에서 철저히 검증해야 불필요한 대기 시간을 줄일 수 있다. 또한 개발 환경 전용 패키지나 절대경로 사용은 서버 실행 실패(크래시/import error)의 주요 원인이 될 수 있다.
7. **최종 순위는 리더보드만으로 결정되지 않는다**: 예선은 자동 점수 중심이지만, 본선은 **기술보고서와 발표의 비중이 상당**하다. 따라서 단순 성능 극대화뿐 아니라 **독창적인 방법론(이론적 기여)** 도 함께 준비하는 것이 유리하다.
