## 1. 데이터가 실제로 말해주는 것 (추측이 아닌 측정)

40개 학습 인스턴스 모두 정상적으로 파싱된다. 뚜렷이 구분되는 두 개의 레짐이 있다:

| | Set 1 (prob 1–20) | Set 2 (prob 21–40) |
|---|---|---|
| 블록 수 n | 100–300 | 100–250 |
| 베이 수 m | 2–5 | 2–4 |
| 시공간 혼잡도¹ | **0.14–0.29** (여유) | **0.29–0.80** (매우 빡빡) |
| 마감일 여유 (D−R−P), 평균 | **~1.2–1.6일** (거의 0) | 2.2–5.4일 |
| 작업 시간 | 3–13 | 5–31 |
| 레이어 수 K | 대부분 1–2, 일부 최대 4 | 동일 |
| 방향 O | 2–8 | 2–8 |
| 다각형 정점 수 | 3–12 (비볼록 허용) | 동일 |
| 전체 기간 | ≤ 약 150일 | ≤ 약 130일 |

¹ 혼잡도 = Σᵢ (최대 레이어 면적 × Pᵢ) / (전체 베이 면적 × 전체 기간). prob_38처럼 0.8에 달하고 형상이 비정형인 경우, 대규모 지연을 피하려면 거의 완벽한 packing 밀도가 요구된다.

**레짐별 함의**
- **Set 1은 스케줄링 문제다.** 여유가 약 1일이라는 것은 거의 모든 블록이 반입일(release time) 또는 그 하루 이내에 반입되어야 마감을 지킬 수 있다는 뜻이다. 공간은 부족하지 않으므로, 솔버는 공간상의 나쁜 이유로 블록 반입을 지연시키는 일이 절대 없도록만 하면 된다. 지연(tardiness)이 게임의 전부다(w1이 매우 큼).
- **Set 2는 패킹 문제다.** 공간이 제약이 되는 구간이며, 혼잡도 ≥ 0.5에서는 어느 정도의 지연이 불가피하다. 여기서 승부는 (a) packing 밀도, 그리고 (b) *어떤 블록을 늦출지 선택*하는 것 — 즉 "모두 제시간에"가 아니라 가중 지연(weighted-tardiness) 트리아지다.
- **가중치는 인스턴스마다 한 자릿수 이상 차이난다** (w1은 667에서 29,630까지, w3은 13에서 600까지). "지연 1일 ≈ (w1/w3) 선호점수"라는 교환비율은 인스턴스에 따라 ~5(prob_32: 선호도가 정말 중요) 에서 ~150(prob_1: 선호도는 타이브레이커에 불과)까지 다양하다. 솔버는 인스턴스별 가중치를 반드시 읽어야 하며, 우선순위를 하드코딩해서는 안 된다.

**baseline 참조 수치 (이 머신, ogc2026 환경에서 측정)**
- prob_1 (쉬움): feasible, obj = 795,089 (obj1 = 26일 지연 → 목적함수의 95%), 37초.
- prob_27 (혼잡도 0.77): **infeasible** (2단계 sweep 충돌이 repair 이후에도 남음)이며 **60초 예산에 247초를 소비** — baseline은 시간 예산도 무시하고 밀집 인스턴스도 처리하지 못한다.

따라서 1차적으로 확보해야 할 두 가지 승리 요소는: naive shapely 루프 대비 ~100배 빠른 기하 엔진, 그리고 repair 기반이 아니라 처음부터 크레인 제약을 인식하는(crane-aware) constructor이다.

## 2. 알고리즘 구조를 결정하는 구조적 통찰

`utils.py` 의미론에 대해 모두 검증 가능한 다음 다섯 가지 관찰이 문제를 상당히 압축시킨다:

**(a) EXIT = ENTRY + P가 약우세(weakly dominant)다.** 반출(exit)을 지연시키는 것은 공간을 더 오래 점유하게 할 뿐이며 지연만 늘릴 수 있다. 반출을 늦출 유일한 이유는 크레인 장애물(다른 블록이 위에 걸쳐있는 경우)뿐인데, 이 자체가 배치의 결과다. 따라서 블록별 실제 결정 벡터는 **(bay, x, y, orient, ENTRY)**이며, exit은 (아래의 인터록킹으로 순서가 강제되는 경우를 제외하면) 파생값이다. 지연은 `max(0, ENTRY + P − D)`가 되며, 각 블록은 "가장 늦은 안전 반입일" `LSE = D − P`를 갖는다.

**(b) "독립 패킹(independence packing)"은 크레인 제약을 소거한다.** j ≥ k sweep 규칙(양방향 모두)이 의미하는 바는: 동시에 존재하는 두 블록의 *레이어 전체를 합친 풋프린트(footprint union)*가 내부적으로 겹치지 않는다면, 반입/반출은 어떤 순서로도 항상 장애물이 없다는 것이다. 풋프린트 유니온이 서로 겹치지 않도록 강제하는 솔버는 크레인 검사가 **전혀** 필요 없다 — 문제가 정수 오프셋을 갖는 동적 2D 비정형 packing으로 환원된다. 이것이 안전하고 빠른 코어 모드다.

**(c) 인터록킹 = 밀도 보너스 + LIFO DAG.** 블록 A의 레이어 k가 블록 B의 레이어 j와 j < k에 대해서만 겹칠 때(즉 A가 B 위로 걸쳐있을 때) 오버랩이 허용된다. 정적 배치와 A의 반입은 문제 없지만, **A가 존재하는 동안 B는 반출될 수 없다**(check_exit이 A의 레이어 j ≥ B의 레이어 k에 걸림). 따라서 모든 오버행 A→B는 "A가 B보다 먼저 반출된다"는 선행관계(같은 날이어도 A의 EXIT이 먼저 기재되면 OK)를 만든다. 즉 인터록킹은 반출 순서의 DAG를 추가하는 *선택적* 밀도 레버이며, set-2 인스턴스에서는 가치 있지만 무분별하게 적용하면 위험하다. 대부분 블록의 K ≤ 2이므로, 실무적으로는 "2레이어 블록의 상단 레이어를, 반출이 더 늦거나 동일한 1레이어 이웃 위로 캔틸레버시킨다"는 패턴이 된다.

**(d) 같은 날 배치(same-day batching)는 공짜 시퀀싱 레버다.** 체커의 2/3단계는 엄격 부등식을 사용한다(동시각 이벤트는 서로를 보지 못함). 5단계는 하루를 *기재된 순서대로 반출 → 기재된 순서대로 반입*으로 리플레이하며, 각 연산을 현재 베이 상태에 대해 검사한다. 따라서 하루 안에서: A가 B를 막고 있었다면 A를 먼저 반출한 뒤 B를 반출하고, A가 비운 공간에 C를 반입할 수 있다. 솔루션 작성기는 같은 날의 반출(위에 걸쳐 있는 블록 먼저)과 반입(걸쳐져 있거나 아래에 있는 블록 먼저)을 위상 정렬해야 한다.

**(e) 시간 차원은 전부 작다.** 정수 일 단위, 기간 ≤ ~150, n ≤ 300. 시간 인덱스 구조(베이별·일별 존재 블록 목록)를 사용해도 비용이 전혀 부담되지 않는다. 공간 차원도 작다(베이 ≤ ~180 × 30 정수 셀, 배치는 정수 (x, y)) — 배치당 후보 앵커 전체 스캔은 후보당 테스트가 O(1)에 가깝다면 배치 하나당 ~5,000개의 저렴한 테스트에 불과하다.

### 3.1 기하 엔진 (force multiplier)

이후 모든 단계는 "초당 몇 개의 배치 후보를 테스트할 수 있는가"에 의해 제약된다. 설계:

- **Tier 1 — 점유 raster.** (block, orientation, layer) 별로 다각형을 유닛 그리드에 미리 래스터화하여 두 개의 비트마스크로 표현한다: *full cells* (셀 ⊆ 다각형)과 *touched cells* (셀 ∩ 다각형 ≠ ∅). (bay, day, layer) 별로 존재하는 블록들에 대해 동일한 두 마스크를 집계 유지한다. 배치 후보 앵커에 대해:
  - touched(new) ∩ full(existing) = ∅ **그리고** full(new) ∩ touched(existing) = ∅ 이고 touched∩touched = ∅ → 경우 분류: touched-only 오버랩 ⇒ *불확실*; full 셀이 관여한 오버랩 ⇒ *확실히 충돌*; touched 오버랩 없음 ⇒ *확실히 자유*.
  - 64비트 워드 단위 비트 AND 연산으로 후보 하나 테스트가 ~마이크로초 수준이다. 한 오리엔테이션에 대한 베이 전체 스캔은 2D 슬라이딩 윈도우 컨볼루션이며 벡터화 가능하다.
- **Tier 2 — 정확 검사(exact check).** *불확실*로 분류된 후보(근접 접촉 배치)만 `utils.py`와 동일한 `area > 0` 의미론을 갖는 정확한 다각형 교차 검사로 넘어간다. 정확성이 중요한 이유는, 접촉은 합법이고 정점이 소수점 4자리라 빡빡한 packing에서 touched-cell 오버랩이 흔하며, 빡빡한 packing이 바로 set 2가 요구하는 것이기 때문이다.
- **구현:** C++ (pybind11), tier 2용 정수 스케일(×10⁴) 다각형 클리핑(Clipper2 또는 직접 구현한 볼록 분해 교차), tier 1용 raw 비트셋 연산. **순수 Python/numpy fallback 필수** — 동일 API(numpy bool 배열 + prepared shapely for tier 2)를 제공하고, 시작 시 try/except import로 선택한다 — 서버에서 `.so` 로드 실패는 성능만 저하시켜야 하며, 결코 정확성을 해쳐서는 안 된다.
- **캐싱:** local search가 재방문하는 (shapeA, orientA, shapeB, orientB, Δx, Δy) 페어에 대해 pairwise 오프셋-실현가능성을 메모이즈한다. 도형별 raster와 shapely prepared geometry도 메모이즈한다(utils가 이미 다각형을 캐싱하므로 exact tier에서 재사용하여 일관성 유지).
- **패리티 하니스:** 수천 건의 무작위 배치를 샘플링하여 엔진의 판정 == `utils.check_entry/check_exit/check_collisions` 판정을 검증하는 테스트. 엔진이 바뀔 때마다 CI에서 실행한다. 불일치는 릴리스 블로커다 — 평가 서버가 곧 utils.py이기 때문이다.

### 3.2 Constructor: 크레인 인식, 이벤트 기반 greedy

t = 0…T일에 대해 시뮬레이션한다. 매일:
1. **반출:** 반출 예정일 = t인 모든 블록에 대해 EXIT을 DAG 위상 순서(위에 걸쳐있는 블록 먼저)로 발생시킨다. 기본 스케줄은 exit = entry + P.
2. **반입:** 반입일이 도래했지만 아직 배치되지 않은 블록들을 우선순위 = `w1 가중 긴급도(LSE − t), 그다음 작업량/크기` (큰 블록은 늦게 배치하기 어려우므로 일찍 배치)로 정렬해 고려한다. 각 블록에 대해:
   - **베이 선택:** score = α·(t..t+P 구간의 공간 가용성, raster 자유면적 기준) + β·w3·선호도 손실 + γ·w2·부하 불균형 변화량. α/β/γ는 인스턴스 가중치(§1의 교환비율 로직)로부터 결정한다.
   - **위치/방향:** 후보 앵커를 기하 엔진에서 *시간 집계* 점유 마스크([t, t+P) 구간에 대한 점유의 합집합 — 위치는 체류 기간 전체 동안 자유로워야 하며, 독립 패킹 하에서는 이것이 유니온 마스크에 대한 단 한 번의 2D 테스트다)에 대해 스캔한다. packing 휴리스틱으로 위치를 채점한다: 빈 공간(enclosure) 낭비 최소화(skyline/contact 보너스가 있는 bottom-left류), 그리고 **반출시각 존닝(exit-time zoning)** — 장기 체류 블록은 베이 안쪽/코너 쪽으로, 단기 체류 블록은 열린 공간 근처로 배치하여 향후 반입에 통로가 필요없게 함(독립 패킹 하에서는 반출이 절대 막히지 않으므로, 존닝은 대신 *향후 배치 가능성*을 보호하는 역할을 한다).
   - t 시점에 배치 가능한 위치가 없으면: 다음 날로 미룬다. `t > LSE`가 되면 해당 블록은 지연 상태로 전환되며, 우선순위를 가중 지연 트리아지로 전환한다(값싸게 늦출 수 있는 블록은 기다리고, 비싼 블록이 공간을 먼저 차지한다; 시간이 아니라 *베이*를 바꾸는 퇴거를 고려한다).
3. obj2를 위해 베이별 부하를 점진적으로 추적하고, obj3은 베이 선택으로부터 얻는다.

빠른 엔진과 결합된 이 constructor만으로도 baseline이 몇 분 걸려도 못하는 것을 몇 초 만에 해낼 수 있어야 하며, (독립 패킹 + 정렬된 같은 날 연산 덕분에) 구성 자체로 feasible해서 repair 단계가 필요 없다. 목표: 각 인스턴스당 10초 이내에 40/40 feasible.

### 3.3 개선 단계: constructor를 decoder로 사용하는 (순서, 배정)에 대한 ALNS

인코딩: 우선순위 시퀀스 + 블록별 (bay, orientation) 힌트. Decoder는 힌트를 feasible한 한 존중하는 이벤트 기반 constructor다. 점수 = 정확한 목적함수(증분 계산이 저렴함: obj1은 반입에서, obj2/obj3은 closed-form).

- **Destroy 연산자:** (i) 최악 지연 블록 + 혼잡 구간의 공간적 이웃; (ii) 한 베이의 무작위 시간창 슬라이스; (iii) 베이 페어 교환 후보(obj2/obj3 타겟); (iv) Shaw 스타일 relatedness(유사 크기 + 시간 중첩).
- **Repair 연산자:** (bay, orient, entry-day, position)에 대한 regret-2/3을 사용한 greedy 재삽입; 이웃의 하루 이동을 허용하는 "squeeze" 재삽입.
- **수락 기준:** 총 목적함수에 대한 simulated annealing, 온도는 w1에 맞춰 스케일(초반에는 하루 지연이 허용되어야 하지만 후반에는 안 됨); 적응형 연산자 가중치(고전적 ALNS 부기).
- **Anytime:** 개선된 feasible 해는 즉시 아카이브에 직렬화된다(메모리 내 + 오케스트레이터가 전역 최선해 유지).

ALNS 외에 가치 있는 지역 탐색: 단일 블록 재최적화(한 블록에 대한 최선의 위치/방향/일자, exact), 블록 페어 베이 교환(obj3/obj2), 반입일 좌측 이동 스윕(공간이 허용하는 한 모든 블록을 최대한 앞당김 — 순수 obj1 이득).

### 3.4 인터록 밀집화기 (set-2 레버, 게이트됨)

Post-pass(추후에는 ALNS repair 변형으로도)로서, 블록이 독립 패킹 하에서 t일에 배치되지 못할 때, 상위 레이어(k ≥ 1)가 exit ≤ 해당 블록 exit인 이웃의 레이어-0과 겹치는 것을 허용하는 재시도를 제안한다(DAG 엣지는 안전한 방향을 가리키며, exact 엔진의 양방향 j ≥ k 검사 전체로 검증한다). exit-선행관계 DAG를 유지한다(솔루션 작성기는 이미 같은 날 연산 순서를 아는 상태). 사이클 = 거부. 이는 엄격히 부가적이다: 절대 발동하지 않아도 독립 패킹 해는 그대로 유지된다. 게이트: 인스턴스 혼잡도 > ~0.35일 때만 활성화하며, M2 지표가 그 가치를 입증한 후에만 활성화한다(가장 버그가 발생하기 쉬운 컴포넌트이므로, 실패 모드는 반드시 "미적용"이어야지 "infeasible"이어서는 안 된다).

### 3.5 매트휴리스틱(선택적, 근거 기반 게이트)

CP-SAT의 두 가지 제한된 용도(ortools 사용 가능; 서버의 Gurobi 라이선스는 후원받았지만 CP-SAT이 더 안전하고 이식성이 좋음):
1. **반입일 재조정:** 모든 블록의 (bay, x, y, orient)를 고정하고, 공간적으로 충돌하는 쌍에 대한 시간상 겹침 없음 제약(disjunctive scheduling 코어) 하에서 정수 반입일을 최적화한다. ALNS가 느리게 찾는 조율된 다중 블록 이동을 잡아낸다.
2. **베이 재배정:** 상대적 packing을 "패턴"으로 고정하고, obj2/obj3에 대해 obj1 추정치와 함께 어떤 패턴/베이 조합을 선택할지 MIP로 결정한다.

M2 이후 프로파일링에서 ALNS가 예산이 남았는데도 정체를 보이는 경우에만 추진한다. critical path에는 포함되지 않는다.

### 3.6 견고성 & anytime 하니스 (타협 불가)

- **예산 관리자:** `timelimit`의 ~8%(대형 한도에서는 최소 20초, 60초 한도에서는 최소 5초)를 다음을 위해 예약한다: 최종 `utils.check_feasibility`, 직렬화, fallback. Constructor는 고정 슬라이스를 받고, ALNS는 중간을 소비하며, 하드 wall-clock은 협조적 검사로 중단한다(시그널 사용 금지 — firejail/cpulimit에 안전해야 함).
- **보장된-실현가능 fallback:** 블록을 한 번에 하나씩 스케줄링하는 단순한 직렬화기(각 블록을 최선의 베이에 순차적으로 단독 배치). 항상 feasible하다(모든 블록은 어떤 베이에 단독으로 들어갈 수 있음), 시작 시 밀리초 단위로 계산되므로, 다른 모든 것이 실패해도 답이 절대 −1이 되지 않는다. 마감 시점 우선순위: 최선 ALNS incumbent → constructor 해 → trivial fallback.
- **최종 게이트:** 로컬 `utils.check_feasibility`를 통과하지 못한 해는 절대 반환하지 않는다. incumbent가 예기치 않게 실패하면(엔진 패리티 버그), 체인을 따라 아래로 fallback한다.
- **예외 처리 위생:** `algorithm()` 최상위에서 try/except로 마지막으로 검증된 해를 반환; 제출 모드에서는 print 없음; 상대 경로만 사용; import는 제공된 패키지 목록으로 제한; 메모리는 16GB보다 충분히 낮게 유지(raster는 기가바이트가 아니라 메가바이트 단위).

## 4. 인스턴스 적응형 정책

시작 시 프로파일러가 계산하는 것: 혼잡도 비율, 여유 분포, 가중치 교환비율, 베이 수/형상, 레이어 수 히스토그램. 이를 기반으로 선택:
- **Set-1 프로파일** (혼잡도 < ~0.3, 여유 ≤ ~2일): constructor는 엄격한 반입일 준수를 우선시하고, ALNS는 예산 대부분을 obj1 좌측 이동과 obj3/obj2 다듬기에 쓴다(obj1이 거의 0에 도달할 수 있으므로); 인터록킹은 꺼둠.
- **Set-2 프로파일:** 가중 지연 트리아지 켬; 인터록 밀집화기 켬(M3 이후); ALNS destroy 연산자는 혼잡 구간에 편향; obj3은 교환비율에 따라 가중치 부여.
- 미지의/hidden 인스턴스는 두 프로파일 사이에 위치할 수 있으므로 — 모든 임계값을 연속적으로(분기 없이) 설계하여 우아하게 성능이 저하되도록 한다. Hidden 인스턴스는 더 *클* 수도 있다(n > 300 또는 베이 > 5): 모든 자료구조는 동적으로 크기를 조정하고, 복잡도는 n × 기간에 대해 거의 선형을 유지하며, 예산의 40%까지 construction이 끝나지 않으면 "패닉 프로파일"(constructor만 + 좌측 이동 다듬기)이 발동한다.

## 5. 마일스톤, 종료 기준, 평가 프로토콜

**평가 하니스 우선 (M0, ~2일).** 40개 인스턴스 전체에 대해 설정 가능한 시간 한도(60/300/900/1800초)로 `algorithm()`을 실행하는 러너를, firejail/cpulimit을 에뮬레이션하는 래퍼(`taskset`/`ulimit`을 통한 4코어, 16GB) 안에서 실행하고, 인스턴스별 (feasible, obj, obj1/2/3, wall time, peak RSS)를 git-SHA 태그와 함께 JSONL 스코어보드에 기록하며, 이전 실행 대비 회귀를 출력한다. 이후의 모든 진척 주장은 반드시 이 스코어보드를 인용해야 한다. 패리티 하니스(§3.1)와 3-시드 분산 리포팅을 포함한다.

| 마일스톤 | 내용 | 종료 기준 (하니스로 측정) |
|---|---|---|
| **M0** (1–2일차) | 하니스, 패리티 테스트, trivial fallback, 예산 관리자 뼈대 | 40/40 실행이 예산 내 완료; fallback 40/40 feasible |
| **M1** (1주차) | 기하 엔진(numpy tier-1 + exact tier-2 먼저; 이후 C++ 포팅), 크레인 인식 constructor | **prob_27/38 포함** 40/40 feasible; construction 각각 10초 미만; baseline이 feasible한 모든 인스턴스에서 obj ≤ baseline obj; 10⁵ 샘플에서 엔진 패리티 불일치 0건 |
| **M2** (2–3주차) | ALNS + 지역 이동 + 포트폴리오 병렬화 + anytime 아카이브 | 300초에서 M1 대비 평균 obj ≥ 30% 개선; 단조 anytime 곡선(60초 obj ≤ 300초 obj ≤ …); 3시드 × 40인스턴스에서 infeasible 0건 |
| **M3** (4주차) | 인터록 밀집화기; 미완이면 C++ 코어; 선택적 CP-SAT 재조정; 레짐별 튜닝 | 혼잡도 > 0.5 인스턴스에서 측정 가능한 set-2 이득(목표 ≥ 10%), feasibility 회귀 0건; 성과 없는 컴포넌트는 폐기 |
| **M4** (마지막 주) | 하드닝: 서버 패리티 드라이런(Ubuntu 24.04, conda 환경, zip 레이아웃, 타겟에서 빌드된 .so), 제출 체크리스트, 시드 고정 | zip이 깨끗한 디렉토리에서 로컬로 end-to-end 검증됨; 3시드 × 4시간한도 전체 스윕 green; 제출 드라이런 문서 |

**제출 주기:** 12시간 쿨다운은 *승인* 시점부터 시작되므로, 모든 제출은 거부 불가능하도록 로컬에서 사전 검증되어야 한다(zip 구조, 루트 레벨 `myalgorithm.py`, 수정되지 않은 `utils.py`, ≤ 15MB, 의심스러운 확장자 없음). M1 시점에 조기 제출하고(모든 인스턴스에서 feasibility만으로도 이미 baseline급 경쟁자를 set 2에서 능가함), 이후 마일스톤마다 제출한다. "마지막으로 확인된 정상" zip을 항상 유지한다.

**리포트/발표(최종 단계 배점이 있음!):** 모든 설계 결정 + ablation을 진행하면서 `docs/experiments.md`에 기록한다(무엇을 시도했는지, 스코어보드 변화, 유지/폐기 여부). §2의 구조적 분석(독립 패킹, LIFO DAG, 같은 날 배치 의미론)은 독창적 방법론 자료이므로 제대로 정리해서 작성한다.

## 7. 즉시 실행할 다음 단계 (M0 착수)

1. 40-인스턴스 하니스 + 스코어보드(`bench/run_bench.py`)를 구축하고, baseline을 첫 추적 대상으로 연결한다.
2. trivial 보장-실현가능 fallback과 예산 관리자 뼈대를 새 `solver/` 패키지 안에 `algorithm()` 엔트리포인트와 함께 구현한다.
3. tier-1 numpy raster 엔진 + tier-2 shapely-패리티 exact check + 패리티 테스트를 구현한다.
4. 독립 패킹 기반의 크레인 인식 constructor를 시작한다; 첫 목표: prob_27과 prob_38을 10초 이내에 feasible하게 만든다.
