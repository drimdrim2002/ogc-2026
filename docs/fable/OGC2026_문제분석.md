# Optimization Grand Challenge 2026 (OGC 2026) 문제 분석
### "The Grand Shipyard Puzzle: Pack the Block, Beat the Clock" — 상세 분석 보고서

> 원문: OGC 2026 Organizing Committee, 2026-06-15 (Document Version 1.2)

---

## 1. 대회 개요

OGC 2026은 **조선소(shipyard)의 블록 배치·스케줄링 문제**를 다루는 최적화 경진대회다. 문제의 본질은 세 가지 하위 문제가 동시에 얽혀 있다는 점이다.

| 하위 문제 | 내용 |
|---|---|
| **배정(Assignment)** | 각 블록을 어느 베이(bay)에 넣을지 |
| **배치(Packing/Layout)** | 베이 내 어느 위치·어떤 방향(orientation)에 놓을지 |
| **스케줄링(Scheduling)** | 언제 반입(ENTRY)하고 언제 반출(EXIT)할지 |

즉, **2D/3D 비정형 도형의 컷팅스톡·패킹 문제 + 병렬 기계 스케줄링 문제 + 자원(공간) 제약을 동시에 푸는 복합 조합최적화 문제**로 요약할 수 있다. 이 세 요소가 서로 독립적이지 않고 상호작용하기 때문에 (베이가 꽉 차 있으면 반입 지연 → 납기 지연 발생 등) 난이도가 매우 높다.

## 2. 문제 정의 (Section 1)

### 2.1 핵심 용어

| 기호 | 용어 | 정의 |
|---|---|---|
| $M=\{1,...,m\}$ | 베이(Bay) | 크기 $W_j \times H_j$의 고정된 작업 공간 |
| $N=\{1,...,n\}$ | 블록(Block) | $K_i$개의 다각형 레이어로 이루어진 3D 구조물, 방향 옵션 수 $O_i$ |
| $R_i$ | 릴리즈 시점 | 블록 $i$가 처리를 시작할 수 있는 가장 이른 시점 |
| $D_i$ | 납기일 | 블록 $i$의 완료 희망 시점 |
| $P_i$ | 처리시간 | 블록 $i$ 처리에 필요한 시간 |
| $ENTRY_i$ | 반입 시점 | 블록이 베이에 놓이는 시점 |
| $EXIT_i$ | 반출 시점 | 블록이 베이에서 나가는 시점 |
| $T_i$ | 지연시간 | $T_i = \max(0, EXIT_i - D_i)$ |
| $L_i$ | 작업량(Workload) | 블록 처리에 필요한 총 작업량 |
| $S_{ij}$ | 선호도 | 블록 $i$가 베이 $j$에 배정되는 것을 선호하는 점수 |

### 2.2 문제 설정 요약

- 하나의 베이에는 **여러 블록을 동시에** 수용할 수 있다 — 단, 공간적으로 겹치지 않아야 함.
- 각 블록은 고유한 $R_i, P_i, D_i$를 가지므로 **공간 배치와 시간 스케줄링을 동시에 고려**해야 실행 가능한 해가 나온다.

### 2.3 베이(Bay) 구조와 크레인 운영 규칙 (매우 중요한 디테일)

- 각 베이는 **독립된 크레인**을 가지므로 베이 간 작업은 서로 간섭하지 않는다.
- 하루 단위(day)로 크레인 오퍼레이션 리스트가 주어지며, **하루에 여러 번의 오퍼레이션(ENTRY/EXIT)** 이 가능하다 (횟수 제한 없음).
- **동일 날짜 내에서는 모든 EXIT 오퍼레이션이 모든 ENTRY 오퍼레이션보다 먼저 수행되어야 한다.** (같은 타입 오퍼레이션 간의 순서는 알고리즘이 자유롭게 정할 수 있음)
- 예시: 처리시간 3, day 5에 ENTRY → **day 8**이 되어야 EXIT 가능 (5, 6, 7일 처리 → 즉 $EXIT_i - ENTRY_i \ge P_i$).
- 블록은 **베이에 놓인 [ENTRY, EXIT) 구간 동안 공간을 점유**한다 (반개구간에 유의).

### 2.4 블록(Block) 구조

- 각 블록은 $K_i$개의 **폴리곤 레이어**(비볼록 가능)로 구성된 3D 구조물이며, 모든 레이어의 높이는 동일하다고 가정.
- "빈 레이어"는 없으며, 인접한 레이어는 반드시 물리적으로 붙어 있다 ("떠 있는" 레이어 불가).
- 블록마다 **미리 정해진 개수의 방향(orientation) 옵션 $O_i$**가 주어진다 (자유 회전 아님, 이산적 후보 방향 중 선택).
- 각 블록은 $L_i$(작업량)와 $S_{ij}$(베이별 선호도 점수)를 가짐.
  - $L_i$는 베이 간 작업량 불균형을 최소화하는 목적함수($Z_2$)에 사용.
  - $S_{ij}$는 선호도 최적화 목적함수($Z_3$)에 사용.

### 2.5 결정 변수 (Section 1.5)

각 블록 $i$에 대해 결정해야 하는 4가지:
1. 배정 베이 $j$
2. 베이 내 위치 $(x, y)$
3. 방향(orientation) 선택
4. $ENTRY_i$, $EXIT_i$

### 2.6 제약 조건 (Section 1.6)

#### (1) 배정 제약 (Assignment Constraints)
- **모든 블록은 반드시 정확히 하나의 베이에 배정**되어야 한다 (미배정 불가).
- 모든 블록은 **정확히 하나의 ENTRY, 하나의 EXIT** 오퍼레이션을 가진다. **한번 놓인 블록은 이동/회전 불가** (재배치 없음).

#### (2) 시간 제약 (Temporal Constraints)
- **릴리즈 제약**: $ENTRY_i \ge R_i$
- **처리시간 제약**: $EXIT_i - ENTRY_i \ge P_i$
- 참고: 통상 $D_i - R_i > P_i$ 이므로 스케줄링에 "슬랙"이 존재 → 다른 블록과의 조율 여지가 생김.
- $EXIT_i > D_i$이면 지연(tardiness) 발생.

#### (3) 공간 제약 (Spatial Constraints) — 가장 복잡한 부분
- **충돌 정의**: 두 블록의 같은 레벨 레이어끼리 **내부(interior)가 겹치면 충돌**. 단, **경계(edge)를 공유하는 것은 충돌 아님** (접촉 허용).
  $$C(\cdot) = \begin{cases}0 & \text{if } int(\cdot)\cap int(\cdot)=\emptyset\\1 & \text{otherwise}\end{cases}$$
- $N(t,j)$ := 시점 $t$에 베이 $j$에 실제로 존재하는 블록 집합 ($ENTRY_i \le t < EXIT_i$).

| 제약명 | 내용 |
|---|---|
| **베이 포함 제약** | 블록은 배정된 베이 경계 안에 완전히 들어가야 함 |
| **레이어 충돌방지 제약** | 같은 시점·같은 베이의 두 블록은 **같은 레벨의 레이어끼리** 충돌이 없어야 함 (레벨 $l=1,...,\min(K_{i1},K_{i2})$까지 검사). 흥미로운 점은 **위에서 봤을 때(top view) 겹쳐 보여도**, 실제로 겹치는 레이어 레벨이 없다면 문제 없음 (도면 7(a) 참고 — 계단식으로 서로 다른 층에서만 접하는 경우) |
| **크레인 오퍼레이션 제약** | 블록을 반입/반출(수직 이동)할 때, 자신의 레이어가 **같거나 더 높은 레벨**에 있는 다른 블록 레이어와 충돌하지 않아야 함. 즉 "위에서 수직으로 내리거나 들어올릴 때 다른 블록에 걸리면 안 됨"이라는 실제 크레인 물리를 반영 |

> **핵심 통찰**: 공간 제약은 단순 2D bin packing이 아니라, **레이어별(높이별) 겹침을 허용하는 3D 유사 패킹** 문제다. 두 블록이 top-view에서 겹쳐 보여도 서로 다른 층에서만 만나면 정적으로는 괜찮지만(레이어 충돌방지), 크레인으로 넣고 뺄 때는 "수직 통로"가 막히면 안 되므로(크레인 제약) 이 두 조건은 별개로 체크해야 한다.

### 2.7 목적함수 (Section 1.7)

세 가지 목표를 가중합하여 최소화:

$$\min\; w_1 Z_1 + w_2 Z_2 + w_3 Z_3$$

| 항 | 이름 | 수식 | 의미 |
|---|---|---|---|
| $Z_1$ | 총 지연시간 | $\sum_i T_i$ | 납기 준수 성능 |
| $Z_2$ | 작업량 불균형 | $\displaystyle\Big\lfloor \max_{j_1 \neq j_2}\Big\vert u_{j_1}\sum_{i\in N(j_1)}L_i - u_{j_2}\sum_{i\in N(j_2)}L_i\Big\vert \Big\rfloor$ | 베이 간 정규화된 작업량 최대 편차 (베이 면적으로 가중치 $u_j$ 보정) |
| $Z_3$ | 선호도 손실 | $\sum_{j}\sum_{i\in N(j)} (S_i^{max} - S_{ij})$ | 최선호 베이 대비 손실 총합 (모두 최선호 베이 배정 시 $Z_3=0$) |

- $u_j = \dfrac{\text{전체 베이 평균 면적}}{W_j \times H_j}$ → **베이가 클수록 가중치가 작음** (큰 베이에 작업량을 몰아도 혼잡도가 낮다는 것을 반영).
- 가중치 $w_1, w_2, w_3$는 인스턴스 JSON에 포함되어 주어짐 (예제: $w_1=26667, w_2=10, w_3=300$ — **가중치 스케일 차이가 매우 크므로, 실제로는 지연시간이 지배적인 목표**가 되는 경우가 많음에 유의).

## 3. 문제 인스턴스 정의 (Section 2, JSON 포맷)

인스턴스 JSON은 4개 최상위 키로 구성:

```
{
  "name": "...",
  "bays": [ {width, height}, ... ],
  "blocks": [ {release_time, due_date, processing_time, workload,
               bay_preferences, shape}, ... ],
  "weights": {"w1":..., "w2":..., "w3":...}
}
```

### 주요 규칙 및 함정 포인트

- **인덱싱**: 인스턴스/솔루션 파일은 **0-based** (수식 정의부인 Section 1은 1-based) — 코드 구현 시 혼동 주의.
- `bay_preferences`: 블록별 각 베이에 대한 선호 점수 리스트. **한 블록의 선호도 합은 항상 100**이 되도록 정규화되어 있음.
- 모든 시간값·선호도값은 **정수(integer)**.
- `shape`: 방향(orientation)별로 딕셔너리 리스트. 각 방향은 `orientation`(ID, 정수) + `layers`(레이어별 폴리곤 정점 리스트, **낮은 레이어→높은 레이어 순**).
  - **레퍼런스 포인트**: 레이어 0의 **첫 번째 정점은 항상 (0.0, 0.0)** — 이것이 기준점이며, 나머지 모든 정점은 이 기준점에 대한 상대 좌표.
  - 블록 위치 $(x,y)$ 지정 시, 기준점을 $(x,y)$로 평행이동하고 나머지 정점들은 상대위치 그대로 유지 → 즉 **방향에 따라 기준점이 항상 좌하단에 오는 것은 아님** (Fig. 8 참고).
  - 정점 좌표는 **소수점 4자리까지의 실수**를 가질 수 있어 수치 불안정성 이슈가 있을 수 있음 → **제공되는 `utils.py`의 함수를 반드시 최종 검증 단계에서 사용 권장** (평가 서버도 동일 함수 사용).

## 4. 솔루션 제출 형식

솔루션은 `{"operations": {날짜: [오퍼레이션 리스트]}}` 형태의 딕셔너리.

- 날짜 키(예: `"0"`, `"1"`, `"28"`)는 오퍼레이션이 있는 날짜만 명시하면 됨 (전체 날짜 나열 불필요).
- 오퍼레이션 타입: `"ENTRY"` (block_id, bay_id, x, y, orient_idx 필요) / `"EXIT"` (block_id, bay_id만 필요).
- **같은 날짜 내에서 모든 EXIT이 모든 ENTRY보다 먼저** 나열되어야 함 (제약 재확인).
- **x, y는 정수여야 함** — 평가 시스템이 반올림 후 `utils.check_feasibility()`로 검사.

### 5.2 평가 결과 상태(status) 종류

| 상태 | 의미 |
|---|---|
| Feasible solution found | 성공, 목적값 표시됨 |
| The solution returned is infeasible | `check_feasibility()` 실패 |
| Time limit exceeded | 시간 제한 초과 (제한 값은 대회 종료 후 공개) |

### 5.4 리더보드 점수 체계

문제당 점수:

$$\text{score} = \begin{cases} -1 & \text{infeasible / TLE / crash} \\ R - n_b & \text{feasible (R=평가팀 수, } n_b\text{=자신보다 더 좋은 목적값을 찾은 팀 수)} \end{cases}$$

- 전체 순위는 **모든 문제의 점수 합산**으로 결정.
- 리더보드는 **정확한 순위가 아니라 티어(top 10/20/30 등)로만 표시**되며, 각 단계 종료 후에만 정확한 순위 공개.
- **최종 수상팀**은 리더보드 점수뿐 아니라 **기술보고서 + 발표**까지 종합 심사하여 결정 (가중치는 조직위 재량).

### 6.3 베이스라인 알고리즘 (Greedy, EDD 규칙)

- **EDD(Earliest Due Date)** 규칙 기반: 납기가 가장 빠른 블록부터 순차 배정.
- 배치 위치는 AABB(축정렬 바운딩박스)의 **우하단 꼭짓점 후보들** 중 선택.
- **1단계에서는 크레인 제약을 무시**하고 배치 → infeasible이 발생하면 2단계에서 **해당 블록을 베이가 빌 때까지 뒤로 미루는 방식**으로 복구.
- 즉, 이 베이스라인은 완전한 하한선 수준이며, **crane 제약을 고려한 배치 순서/위치 최적화**가 실질적인 성능 개선 포인트로 시사됨.

### 6.4 비-Python 언어 사용

- C/C++: **로컬에서 Ubuntu 24.04 기준으로 컴파일 후** `.so`/실행파일을 zip에 포함 (서버 측 컴파일 없음).
- Java: OpenJDK 17.0.18 제공. .NET: 8.0.15 제공.
- 비-Python 구현 시 서버 환경과의 호환성·격리는 전적으로 팀 책임.

### 6.5 알고리즘 테스터 & 시각화 도구

- `alg_tester.zip` 다운로드 → `ogc2026` conda 환경에서 `python alg_tester_app.py` 실행.
- Problem/Solution 탭에서 베이별 단면도(cross-sectional view)로 블록 배치 확인 가능, Gantt 차트로 시간축 확인 가능.

## 7. 대회 진행 방식 (Section 5)

```
예선(Preliminary) ──▶ 본선(Final) 진출팀 30~40개 선발
        │                        │
   자동평가(리더보드)      자동평가 + 기술보고서 + 발표
        │                        │
   티어별 표시(정확한       종합심사로 최종 수상팀 결정
   순위는 단계 종료 후 공개)  (자동점수+보고서+코드+발표 종합)
```

### 7.1 예선 단계
1. 자동 평가 → 티어 기반 리더보드 갱신
2. 조직위의 **코드 검증** 병행 → 상위 30~40팀 본선 진출

### 7.2 본선 단계
1. 자동 평가 (예선과 동일 방식)
2. **기술보고서** 제출 필수 (코드+보고서 별도 심사)
3. **발표(Presentation)** 필수
4. 자동점수·보고서·코드·발표를 종합하여 **최종 수상팀** 결정

### 7.3 평가·공개·윤리 (Section 5.3)

- 개별 평가 결과는 **비공개** (수상팀 순위만 공개).
- **본선 진출팀의 코드·보고서는 전부 오픈소스로 공개**됨에 동의해야 참가 가능.
- 대회 종료 후에도 **표절·제한 자원 무단 사용 등 부정행위 발견 시 수상 취소** 가능.

## 9. 핵심 난이도 요약 및 전략적 시사점 (분석)

1. **혼합 정수 비선형/조합 문제**: 배정(할당) + 2D 비정형 도형 패킹(방향 선택 포함) + 시간 스케줄링이 동시에 결합 → 순수 MIP로 완전히 정식화하면 규모가 커질수록 Gurobi/Xpress로도 대형 인스턴스는 시간 내 최적해 도출이 어려울 가능성이 높음. **메타휴리스틱/휴리스틱 배치 + 국소 탐색(local search)/제약 완화 후 복구** 조합이 현실적 접근으로 보임.
2. **크레인 제약이 진짜 함정**: 단순 "겹침 없음"만 체크하면 안 되고, **반입/반출 시점에서 수직 통로가 막히는지**까지 별도로 검증해야 한다. 베이스라인도 이 부분을 1단계에서 무시하고 사후 복구하는 방식을 취함 — 처음부터 이를 고려한 배치 순서(스택 형태로 나중에 뺄 블록을 안쪽에 넣지 않기 등) 설계가 핵심 개선 포인트.
3. **목적함수 가중치의 스케일 불균형**: 예시 가중치($w_1=26667$ vs $w_2=10$, $w_3=300$)를 볼 때, $Z_1$(총 지연시간) 값 자체는 작지만 가중치가 매우 커서 **사실상 납기 준수가 지배적 목표**가 될 가능성이 큼 — 인스턴스별 가중치를 반드시 확인해서 우선순위를 조정해야 함.
4. **레이어 단위 충돌 판정의 이점 활용**: "위에서 보면 겹쳐도 실제 레이어 레벨이 다르면 무방"이라는 규칙(Fig. 7(a))은, **블록들을 계단식/맞물림 형태로 배치해 공간 효율을 크게 높일 수 있는 여지**를 의미함. 단순 사각형 패킹보다 공간 활용률을 높일 수 있는 포인트.
5. **수치 안정성**: 정점 좌표가 소수점 4자리 실수이므로 부동소수점 오차로 인한 거짓 충돌/거짓 통과 가능성 → 반드시 제공된 `utils.py`(Shapely 기반으로 추정)의 판정 함수를 그대로 재사용해 평가 서버와 동일한 기준으로 검증해야 함.
6. **제출 운영상 리스크 관리**: 12시간 쿨다운은 "승인된" 제출 기준이므로, 거절 사유(zip 구조, 경로, 크기 등)를 사전에 로컬에서 철저히 검증해 불필요한 대기시간 낭비를 막아야 함. 또한 개발환경 전용 패키지·절대경로 사용은 서버 실행 실패(크래시/임포트 에러)의 주요 원인이 될 수 있음.
7. **최종 순위는 리더보드만으로 결정되지 않음**: 예선은 자동채점 중심이지만, 본선은 **기술보고서·발표 비중이 상당**하므로, 단순 성능 극대화 외에 **독창적 방법론(이론적 기여)**을 함께 준비하는 것이 유리함.
