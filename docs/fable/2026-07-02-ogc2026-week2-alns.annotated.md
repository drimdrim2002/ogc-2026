### 0.2 ALNS(Adaptive Large Neighborhood Search)란 무엇인가

> 💡 **설명 — 메타휴리스틱 경험이 있다면 가장 빨리 감을 잡는 방법은 "국소탐색(local search)의 확장판"으로 보는 것입니다.**
>
> **LNS(Large Neighborhood Search)의 기본 아이디어**: 일반적인 국소탐색은 해를 "아주 조금만"(예: 두 원소 swap) 바꿔가며 개선을 찾습니다. LNS는 그 대신 해의 **큰 덩어리를 한 번에 무너뜨렸다가(destroy) 다시 그럴듯하게 재조립(repair)**하는 방식으로 훨씬 넓은 이웃해(neighborhood)를 탐색합니다. 이 프로젝트로 치면:
> 1. **Destroy(파괴)**: 현재 배치(incumbent)에서 블록 몇십 개를 골라 **제거**합니다 — 이 상태는 "부분해"(일부 블록만 배치된 상태)가 됩니다.
> 2. **Repair(복구)**: 제거된 블록들을 다시 어딘가에(다른 bay, 다른 시각일 수도 있음) **삽입**해 다시 완전한 해로 만듭니다.
> 3. 새로 만든 완전해가 이전보다 좋아졌으면 채택하고, 아니어도 일정 규칙(수용 기준)에 따라 채택할 수도 있습니다.
> 4. 이 destroy→repair→(수용 판정) 사이클을 시간 예산이 다할 때까지 계속 반복합니다.
>
> 왜 이게 단순 국소탐색보다 유리한가: "블록 하나만 옮기기"로는 절대 벗어날 수 없는 나쁜 배치 패턴(예: 여러 블록이 서로 얽혀 지각을 유발하는 뭉치)도, "그 뭉치를 통째로 뜯어서 다시 짜면" 빠져나올 수 있기 때문입니다.
>
> **"Adaptive"(적응적)가 붙는 이유**: destroy 방법도, repair 방법도 한 가지만 쓰지 않고 **여러 개(이 프로젝트는 파괴 6종 + 복구 4종)를 후보로 두고, 매 반복마다 하나씩 무작위로 골라 씁니다.** 이때 "완전 균등 확률로 고르기"보다 한 단계 발전시켜, **최근에 성과가 좋았던 연산자를 더 자주 뽑히게** 확률(가중치)을 조금씩 조정할 수 있습니다 — 이게 "적응"입니다. 이 프로젝트는 설계서에 근거해 **기본값은 이 적응을 끄고(정적 균등 확률) `--adaptive` 플래그로만 켜도록** 설계했습니다(0.6절에서 이유 설명).
>
> 정리하면 ALNS는 "여러 개의 파괴 방법 × 여러 개의 복구 방법을 필요에 따라 골라 쓰면서, 파괴→복구를 무한 반복해 해를 계속 개선해나가는" 메타휴리스틱입니다. 1주차의 `construct()`가 "한 번에 처음부터 끝까지 순서대로 배치해서 해 하나를 만드는" 함수였다면, 2주차의 `improve()`는 "이미 있는 해를 받아서 부수고 고치기를 반복하며 계속 더 좋게 만드는" 함수입니다.

### 0.3 파괴(destroy) 연산자 6종 — 무엇을 부수는가 (직관만 먼저, 상세는 Task 3·4)

| 연산자 | 부수는 대상 | 직관 |
|---|---|---|
| **random** | 무작위 블록 집합 | 순수 다양화. 아무 편향 없이 매번 다른 조합을 시도. |
| **worst_tardiness** | 지각이 가장 심한 블록들 | "문제가 되는 블록부터 뜯어서 다시 짜보자." |
| **shaw (관련도)** | 서로 "가까운"(공간·시간상 근접) 블록들의 군집 | 서로 얽혀있는 덩어리를 통째로 뜯어야 재배치 여지가 생기므로. |
| **time_slice** | 한 bay의 특정 시간대에 걸쳐있는 블록 전부 | "이 시간대 이 bay를 통째로 비우고 다시 채워보자." |
| **spatial_column** | 한 bay의 특정 x축 구간(기둥 모양)에 걸쳐있는 블록 전부(시간 무관) | "이 공간 영역을 통째로 비우고 다시 채워보자." |
| **blocking_set** (문제 특화) | 지각 블록이 "더 일찍 들어오지 못하게 막고 있는" 방해 블록들 | 지각의 근본 원인(누가 길을 막고 있는가)을 역추적해서 제거. |

### 0.4 복구(repair) 연산자 3계열 — 어떻게 다시 채우는가 (직관만 먼저, 상세는 Task 5·6)

- **greedy_noise**: ATC 순서(1주차 기계장치 재사용)대로 하나씩, 매번 "지금 봤을 때 가장 싼 곳"에 넣되 비용에 약간의 무작위 잡음을 곱해 매번 다른 선택을 하게 함.
- **regret-2 / regret-3**: 아래에서 자세히 설명하는 "후회(regret)" 개념 기반 — "지금 최선 자리에 못 넣으면 나중에 얼마나 손해볼지"가 큰 블록부터 먼저 확정.
- **most_constrained_first**: "선택지가 가장 적은(꽉 막힌) 블록부터" 먼저 넣는 방식 — CSP(제약만족문제)의 MRV(Minimum Remaining Values) 휴리스틱과 같은 발상.

> 💡 **설명 — regret-k(후회값)이란 정확히 무엇인가:** 그리디(greedy) 알고리즘의 흔한 함정은 "지금 당장 제일 싼 수를 두다 보면, 나중에 배치할 블록이 더 나쁜 자리밖에 못 골라 크게 손해보는" 상황입니다. **regret-k**는 이걸 미리 감지하는 지표입니다: 어떤 블록을 놓을 수 있는 여러 후보 자리(bay)들의 비용을 오름차순으로 정렬했을 때, `regret = (2번째로 싼 비용 − 1번째로 싼 비용) + (3번째로 싼 비용 − 1번째로 싼 비용) + ...`(k개 항)로 계산합니다. 이 값이 **크다는 것은 "지금 1등 자리를 놓치면 대안들이 훨씬 비싸진다"**는 뜻이므로, **regret이 큰 블록을 먼저 확정**해서 그 블록의 좋은 자리를 다른 블록에게 뺏기지 않게 지킵니다. `regret-2`는 k=2(1·2등 차이만), `regret-3`은 k=3(1·2·3등 차이 합)까지 봅니다. 대안이 k개보다 적은 블록(예: bay가 1개밖에 안 맞는 블록)은 "가상의 아주 비싼 대안"(M, 큰 상수)을 채워 넣어 "이 블록은 선택의 여지가 없으니 최우선으로 취급해야 한다"는 신호를 강하게 줍니다. 이런 방식은 VRP(차량경로문제)·기계배정 등 삽입 기반 휴리스틱에서 표준적으로 쓰이는 기법입니다.

### 0.5 수용 기준(acceptance criteria) — RRT vs SA (직관만 먼저, 상세는 Task 7)

파괴→복구로 새 해(candidate)를 만들었을 때, "이걸 현재 해로 삼을지 버릴지"를 정하는 규칙입니다. 단순 언덕오르기(hill-climbing, "더 좋을 때만 채택")는 국소최적(local optimum)에 갇히기 쉬워서, 이 프로젝트는 두 가지 대안을 씁니다.

- **RRT(Record-to-Record Travel, 기본값)**: "지금까지 찾은 최고 기록(best, record)"보다 **일정 허용폭(threshold) 이내로만 나쁘면** 그 해를 현재 해로 받아들입니다. 이 허용폭은 시간이 지날수록(탐색이 진행될수록) 점점 줄어들어(선형 감소) 나중엔 사실상 개선만 받아들이게 됩니다.
- **SA(Simulated Annealing, 담금질 기법, 대안)**: 물리학의 "금속을 서서히 식히면 원자가 최적 격자 구조를 찾아간다"는 담금질 과정을 흉내낸 기법. "온도(T)"가 높을 때는 다소 나빠지는 해도 확률적으로(`exp(-Δ/T)`, 볼츠만 분포) 받아들이고, 온도가 낮아질수록(alpha를 곱해 서서히 냉각) 점점 더 개선만 받아들이게 됩니다. 이 프로젝트는 온도가 너무 식어 정체되면 다시 데우는 **재가열(reheat)** 장치까지 넣었습니다.

> 💡 **설명 — 왜 단순 언덕오르기보다 나은가:** 둘 다 "가끔은 일부러 손해를 감수"하는 것이 핵심입니다. 파괴→복구로 만든 해가 당장은 조금 나빠 보여도, 그 해에서 출발해야만 도달할 수 있는 더 좋은 영역이 있을 수 있습니다(탐험 vs 활용의 균형, exploration vs exploitation). 둘 다 "탐색 초반엔 너그럽게, 후반엔 깐깐하게"라는 공통 원리를 갖지만, RRT는 "최근 기록(best) 대비 절대적 허용폭"으로 단순하고 결정적인 반면, SA는 "확률적 수용 + 온도"라는 더 유연하지만 파라미터가 많은 방식입니다. 설계서 근거 문헌(Santini, Ropke & Hvattum 2018)이 RRT를 권장해 기본값으로 채택했습니다.

### 0.6 AlnsConfig / ablation(`--disable-op`)이 왜 필요한가

`AlnsConfig`는 이번 주 만드는 모든 튜닝 파라미터(제거율, 수용 기준 종류, 적응 여부, Shaw 가중치 등)를 한 군데 모은 설정 객체입니다(Task 9에서 정의). 각 필드의 의미는 본문에서 등장할 때 설명합니다.

> 💡 **설명 — ablation(제거 실험)이 왜 필요한가:** "파괴 6종 + 복구 4종을 다 넣었더니 좋아졌다"까지는 쉬운데, **그중 어느 연산자가 실제로 기여했는지**는 알 수 없습니다. 어떤 연산자는 있으나 마나이거나 심지어 방해가 될 수도 있습니다. `--disable-op NAME` 플래그로 연산자를 하나씩 꺼가며 벤치마크를 반복하면, "이 연산자를 껐더니 결과가 확 나빠졌다"(중요한 연산자) 또는 "껐는데 별 차이 없다"(불필요할 수 있는 연산자)를 실측으로 구분할 수 있습니다. 이건 머신러닝의 ablation study(구성요소 하나씩 제거하며 기여도 측정)와 완전히 같은 방법론이고, Task 13에서 실제로 10개 연산자 각각을 꺼가며 8개 인스턴스에 대해 이 실험을 수행합니다.

# OGC 2026 — 2주차: ALNS 코어 (파괴 6 + 복구 3, RRT 수용, 증분 평가, NFP Minkowski 가속) 구현 계획

**Goal:** 1주차 구성해(multi-start construct) 위에서 300초 예산 기준 Z1(tardiness)을 20% 이상 줄이는 ALNS 개선 루프를 `shell.improve()` 훅에 연결하고, 전 40개 인스턴스 feasible을 유지한다.

**Architecture:** ALNS는 순수 Python(`solver/alns/`)으로 구현하되 모든 기하 질의는 1주차 `ogc_core.Core` API(`place/remove/earliest_feasible/free_positions`)에 배치 호출한다. 해 상태는 "placements 리스트가 유일한 정본"이며, `SolutionState`가 Core 반영 + 증분 목적함수(Z1 델타, Z2/Z3 O(n) 재계산) + snapshot/restore(파괴-복구 실패·거부 시 롤백)를 관장한다. 성능 전제인 NFP 비트맵 생성은 오프셋 전수 스캔(v0)을 Clipper2 MinkowskiSum 기반(v1)으로 교체하되 **v0과 비트 단위 동일**을 테스트로 강제한다.

> 💡 **설명 — 이 문단이 2주차 설계 요약입니다.**
> - **"순수 Python(`solver/alns/`)으로 구현"**: 1주차가 "빠른 부분은 C++, 조립은 Python"이었다면, 2주차 ALNS 로직(어떤 블록을 뽑고, 어떻게 순서를 매기고, 언제 받아들일지 등)은 전부 Python으로 짭니다. 다만 "충돌 판정" 같은 무거운 기하 계산은 여전히 C++ 코어에 위임합니다 — "기하는 코어에게, 알고리즘 흐름은 Python에게"라는 역할 분담입니다.
> - **"모든 기하 질의는 ... 배치 호출한다 (충돌 검사 1회 단위의 잦은 왕복 금지)"**: pybind11 호출 하나하나에는 미세하지만 고정 오버헤드가 있습니다(설계서 기준 ~0.1~0.3µs). 이걸 블록 하나 옮길 때마다 수백 번씩 부르면 그 오버헤드가 누적되어 느려집니다. 그래서 "이 블록을 놓을 수 있는 가장 빠른 시각과 위치"처럼 **한 번의 호출로 큰 단위의 일을 끝내는** `earliest_feasible`, `free_positions` 같은 API를 씁니다(1주차에서 이미 이렇게 설계됨) — ALNS도 이 원칙을 그대로 따릅니다.
> - **"placements 리스트가 유일한 정본(canonical)"**: 해의 "진짜 데이터"는 `(block, bay, x, y, orient, entry, exit)` 튜플들의 리스트 하나뿐이라는 뜻입니다. Core 내부 상태, `SolutionState`의 장부(Z1/Z2/Z3 누적값) 등은 전부 이 리스트에서 파생된 "캐시"일 뿐이며, 이 리스트와 항상 일치해야 합니다. 이렇게 "정본은 하나"로 못박아두면 "어느 쪽 상태가 맞는 상태인가"를 헷갈릴 여지가 없어집니다.
> - **"증분 목적함수(Z1 델타, Z2/Z3 O(n) 재계산)"**: 블록 하나를 빼거나 넣을 때마다 Z1/Z2/Z3 전체를 처음부터 다시 계산하면 느립니다(블록 수 n에 비례하는 시간이 매번 듦). 대신 "이번에 바뀐 블록 하나 때문에 값이 얼마나 바뀌었는지"만 계산해서 누적 장부에 더하거나 빼는 방식(증분, incremental)을 씁니다. Z1은 "이 블록의 지각분"만 더하고 빼면 되므로 O(1), Z2(bay별 부하 최대-최소)는 "부하 배열이 바뀔 때마다 다시 최대-최소를 구해야" 해서 bay 개수만큼(O(n_bays), 사실상 상수) 걸립니다. (Task 2에서 구현 상세)
> - **"snapshot/restore(파괴-복구 실패·거부 시 롤백)"**: 파괴→복구를 시도했는데 복구가 실패했거나(모든 블록을 다시 못 넣음), 성공은 했지만 결과가 나빠서 수용 기준이 거부했다면, **시도 이전 상태로 되돌려야** 합니다. `snapshot()`으로 "지금 상태"를 저장해두고, 실패 시 `restore()`로 되감는 이 패턴은 트랜잭션의 롤백(rollback)과 같은 개념입니다 — 메타휴리스틱에서 "이웃해를 찔러보고 안 되면 원상복구"하는 매우 흔한 구현 패턴입니다.
> - **"NFP 비트맵 생성은 ... v0을 ... v1으로 교체하되 v0과 비트 단위 동일을 테스트로 강제"**: 1주차 0.5절/Task 4에서 예고했던 대로, 이번 주에 드디어 "느리지만 확실한 방법(v0, 오프셋 하나하나 다 검사)"을 "빠른 기하 연산 한 방(v1, Minkowski 합)"으로 바꿉니다. 다만 "빠르게 바꿨더니 답이 미묘하게 달라졌다"는 사고를 막기 위해, 두 버전이 **모든 비트가 완전히 똑같이 나오는지**를 자동 테스트로 강제합니다(Task 1).

**Tech Stack:** Python 3.12, C++20 + Clipper2(vendored) + pybind11 (1주차 빌드 파이프라인 그대로), pytest, `baseline/utils.py`(최종 oracle).

> 💡 **설명:** 대부분 1주차와 동일한 제약의 재확인입니다. 새로 강조할 부분만 짚으면 — "**ALNS는 자체 기하 판정을 절대 하지 않는다**"는 이번 주 설계의 핵심 원칙입니다. 파괴·복구 연산자가 아무리 창의적인 방식으로 블록을 고르고 옮기더라도, "이 자리에 놓아도 되는가"를 직접 계산하지 않고 반드시 1주차 Core의 `place/check_place/earliest_feasible` 등을 통해서만 묻습니다. 이렇게 해야 "충돌 판정 로직이 여러 군데 흩어져서 서로 미묘하게 달라지는" 위험을 원천 차단할 수 있습니다(1주차에서 그토록 공들여 만든 fuzz/oracle 검증의 신뢰를 그대로 물려받는 방법이기도 합니다). "**적응 가중치는 ... 기본은 정적 균등**"은 0.6절/0.2절에서 이미 예고한 대로, 문헌상 적응층의 기여가 미미하다는 근거(Turkeš et al. 2021, 기여 ~0.14%)에 따른 설계 선택입니다.

```python
.accept(cand_obj, cur_obj, best_obj, progress, rng) -> bool     # 두 클래스 공통
make_acceptance(cfg, initial_obj) -> RecordToRecord | ReheatedSA

# solver/alns/weights.py
OperatorSelector(names, adaptive=False, segment=100, scores=(33,13,9), reaction=0.1)
.select(rng) -> str ; .reward(name, kind) ; .tick() ; .stats() -> dict
# kind ∈ {"best","better","accepted"}

# solver/alns/loop.py
AlnsConfig(enabled=True, removal_rate=0.33, acceptance="rrt", rrt_start_pct=0.03,
           sa_start_pct=0.05, adaptive=False, segment=100, scores=(33,13,9), reaction=0.1,
           shaw_weights=(0.55,1.36,0.89), shaw_p=6, noise=0.1, disable_ops=(),

# trace: 호출자가 준 list에 (elapsed_sec, best_obj) append. stats: dict에 iters/연산자 통계 기록.
# 반환 해는 완전 배치(len == n_blocks)이며 항상 incumbent 이하의 objective.
```

> - `.placed: dict[int, Placement]`가 **"canonical state의 dict 뷰"**라는 표현: 앞서 Architecture 문단에서 "placements 리스트가 유일한 정본"이라 했는데, `SolutionState` 내부에서는 이걸 굳이 리스트가 아니라 `{block_id: placement}` **딕셔너리**로 들고 있습니다. 왜냐하면 destroy/repair 연산자들은 "블록 5번을 빼고, 블록 12번을 넣고" 식으로 **특정 블록 id로 빈번하게 접근**해야 하는데, 리스트에서 특정 id를 찾으려면 매번 훑어야 하지만(O(n)) 딕셔너리는 즉시 찾아집니다(O(1)). `.placements()`가 필요할 때만 `sorted(self.placed)` 순서로 리스트를 만들어 반환하는 식으로 "겉보기엔 리스트가 정본, 내부 구현은 딕셔너리"를 절충합니다.
> - **`.z2_with(bay, dw)`**: "이 bay에 워크로드 dw만큼을 추가로 얹으면 Z2가 얼마가 될까?"를 **실제로 배치하지 않고** 미리 계산해보는 함수입니다. 복구 연산자가 "이 블록을 이 bay에 넣으면 비용이 얼마나 늘까"를 여러 후보 bay에 대해 비교해야 하는데, 매번 진짜로 넣었다 뺐다 하면서 확인하면 느립니다. 이런 "실제로 커밋하지 않고 가정만 해서 비용을 미리 계산"하는 패턴은 삽입 기반 휴리스틱(construction heuristic)에서 아주 흔합니다 — 뒤에 나올 `insertion_cost`가 바로 이 함수를 사용합니다.
> - **`Candidate = tuple[cost, bay, x, y, orient, entry]`**: 복구 연산자들이 공통으로 주고받는 "후보 삽입안" 하나를 표현하는 튜플입니다. 첫 원소가 `cost`이므로 파이썬 튜플 비교(`min()`, `<`)를 그대로 쓰면 "비용이 가장 싼 후보"가 자동으로 골라집니다(1주차 디코더의 사전식 비교와 같은 관용구).
> - **`repair_*(...)  -> bool`**: 복구 함수들이 배치 자체를 반환하지 않고 **성공 여부(bool)만** 반환한다는 점이 중요합니다. 실제 배치 결과는 `state`(SolutionState) 안에 이미 반영되어 있으므로(부작용으로 상태를 바꾸는 함수), 실패 시(`False`) 호출자가 `state.restore(snapshot)`으로 되돌리면 됩니다 — 위 Architecture 설명의 롤백 패턴이 API에 그대로 녹아있습니다.
> - **`accept(...).accept(cand_obj, cur_obj, best_obj, progress, rng) -> bool`**: RRT와 SA 두 클래스가 **똑같은 메서드 시그니처**를 가지므로, `loop.py`(Task 9) 입장에서는 어느 쪽을 쓰든 코드를 바꿀 필요가 없습니다 — 객체지향의 "다형성(polymorphism)"을 아주 가볍게(공식 인터페이스/추상클래스 없이 "덕 타이핑"으로) 활용한 예입니다. `progress`는 "예산을 얼마나 소진했는가"(0=시작, 1=예산 소진)를 나타내는 값으로, RRT의 허용폭 선형 감소·SA의 관점에서 공통으로 쓰입니다.
> - **`OperatorSelector.reward(name, kind)`의 `kind ∈ {"best","better","accepted"}`**: 방금 쓴 연산자가 낸 결과가 "지금까지 중 최고 기록을 경신"(best)했는지, "이전 시도보다는 나아졌지만 기록 경신은 아님"(better)인지, "나빠졌지만 수용 기준이 받아들여줌"(accepted)인지에 따라 **점수를 차등 지급**(설계서 σ=33/13/9)합니다. 최고 기록을 낸 연산자에게 가장 큰 보상을 주는 것이 직관적입니다.

기존 v0의 "윈도 전 오프셋 × overlap_pos_area" 채움 루프를 `fill_bitmap_scan`으로 함수 분리하고(윈도 계산 코드는 공용 헬퍼 `bitmap_window(...)`로 추출 — v0/v1이 **동일 윈도**를 쓰는 것이 비트 동일성의 전제), 다음을 추가:

```cpp
#include "clipper2/clipper.h"
#include <cstdlib>
using namespace Clipper2Lib;

// t ∈ interior(A ⊕ (−B))  ⇔  int(A) ∩ int(B+t) ≠ ∅  ⇔  겹침 면적 > 0 (v0와 동일 의미론).
// 좌표는 SCALE 정수, 오프셋은 SCALE의 배수 → 모든 판정이 정수 정확.
static Paths64 mink_collision_region(const Path64& a, const Path64& b) {
    Path64 nb; nb.reserve(b.size());
    for (const auto& pt : b) nb.push_back(Point64(-pt.x, -pt.y));
    Paths64 sum = MinkowskiSum(a, nb, /*isClosed=*/true);
    return Union(sum, FillRule::NonZero);   // 방향 정규화(양면적=외곽, 음면적=구멍)
}

// 경계 위(IsOn) = 접촉 = 비충돌(v0의 area>0 의미론과 일치). 구멍은 winding으로 제외.
static bool point_strictly_inside(const Paths64& region, const Point64& p) {
    int wind = 0;
    for (const auto& path : region) {
        auto r = PointInPolygon(p, path);
        if (r == PointInPolygonResult::IsOn) return false;
        if (r == PointInPolygonResult::IsInside) wind += (Area(path) > 0) ? 1 : -1;
    }
    return wind > 0;
}

// layers_a/layers_b: 두 shape의 스케일 정수 레이어 다각형 (1주차 ShapeTable에 이미 존재).
// combos: kind에 따른 레이어 조합 목록 (static: k×k, entry: k×j (j≥k)) — v0의 조합 생성 코드를
//         함수로 추출해 scan/mink가 공유. bm은 bitmap_window()가 만든 빈 비트맵 (v0와 동일 윈도).
void fill_bitmap_mink(OffsetBitmap& bm,
                      const std::vector<Path64>& layers_a,
                      const std::vector<Path64>& layers_b,
                      const std::vector<std::pair<int,int>>& combos) {
    for (const auto& [ka, kb] : combos) {
        Paths64 region = mink_collision_region(layers_a[ka], layers_b[kb]);
        if (region.empty()) continue;
        for (int iy = 0; iy < bm.h; ++iy)
            for (int ix = 0; ix < bm.w; ++ix) {
                if (bm.get(ix, iy)) continue;  // 이미 hit이면 스킵
                Point64 p(int64_t(bm.dx_lo + ix) * SCALE, int64_t(bm.dy_lo + iy) * SCALE);
                if (point_strictly_inside(region, p)) bm.set(ix, iy);
            }
    }
}

static bool use_scan_method() {
    const char* m = std::getenv("OGC_NFP_METHOD");
    return m && std::string(m) == "scan";
}
```

v0 채움 루프도 같은 꼴의 `fill_bitmap_scan(bm, layers_a, layers_b, combos)`로 분리(내용은 기존 "오프셋별 overlap_pos_area OR" 그대로). `static_bm`/`entry_bm`의 lazy 빌드 지점은 `bitmap_window()`로 빈 비트맵을 만든 뒤 `use_scan_method() ? fill_bitmap_scan(...) : fill_bitmap_mink(...)`를 호출. `OffsetBitmap`에 `get(ix,iy)/set(ix,iy)`가 없다면 이 Task에서 추가(비트 인덱스 `iy*w+ix`).

> 💡 **설명 — Minkowski Sum(민코프스키 합)이 무엇이고, 이 코드가 그걸로 왜 NFP를 구하는가:**
> **민코프스키 합** `A ⊕ B`는 "도형 A의 모든 점 + 도형 B의 모든 점"을 다 더한 결과로 만들어지는 새로운 도형입니다(집합 `{a + b : a ∈ A, b ∈ B}`). 직관적으로는 "도형 B를 A의 윤곽선을 따라 쭉 미끄러뜨리며 쓸고 지나간 자국 전체"라고 이해하면 됩니다.
>
> 여기서 쓰는 건 정확히는 `A ⊕ (−B)`(B를 원점 기준으로 뒤집은 것과의 합)입니다. 이렇게 하면 **"B를 오프셋 t만큼 이동시켰을 때 A와 겹치는가?"라는 질문의 답이 정확히 "t가 A ⊕ (−B) 영역 안에 있는가?"와 같아집니다.** 즉, 오프셋 하나하나를 따로따로 검사하는 대신(v0의 방식), **"충돌이 일어나는 모든 오프셋의 집합"을 기하 연산 딱 한 번으로 통째로 구해버리는** 것이 Minkowski 기반 NFP의 핵심 아이디어입니다(1주차에서 "NFP" 개념을 처음 소개할 때 이미 이 이름의 유래를 언급했었습니다).
>
> 코드를 뜯어보면:
> - `nb`(negated b): B의 모든 정점 좌표에 `-1`을 곱해 원점 대칭시킨 도형 `−B`입니다.
> - `MinkowskiSum(a, nb, true)`: Clipper2 라이브러리가 제공하는 함수로 `A ⊕ (−B)`를 계산합니다.
> - `Union(sum, FillRule::NonZero)`: Minkowski 합 계산 결과가 여러 조각(경우에 따라 자기교차나 방향이 뒤섞인 폴리곤들)으로 나올 수 있어, 이를 하나로 정리(합집합)하며 "바깥 경계=양의 면적, 구멍=음의 면적"으로 방향을 통일합니다(1주차에서 본 `FillRule::NonZero`가 여기서도 같은 역할).
> - `point_strictly_inside`: 정리된 영역(`region`)에 대해 "이 점(오프셋 좌표)이 영역 안쪽에 진짜로 들어있는가"를 winding number(감김 수) 방식으로 판정합니다. **`IsOn`(경계 위)이면 즉시 false**로 처리하는 것이 중요한 디테일 — 경계에 걸친다는 것은 "접촉"이라는 뜻이고, 1주차 Task 3에서 이미 정한 원칙("접촉은 충돌이 아니다")과 정확히 일치시키기 위함입니다. 구멍(hole, 음의 면적으로 표시된 영역)은 `wind -= 1`로 상쇄되어 "구멍 안쪽"은 최종적으로 충돌 아님으로 처리됩니다.
> - 바깥의 `fill_bitmap_mink`는 이렇게 구한 영역을, 여전히 **비트맵의 모든 칸(ix, iy)에 대해 "이 칸이 영역 안에 있는지" 하나씩 확인**해서 채웁니다. "오프셋별로 폴리곤 교차 계산을 매번 새로 하는" v0와 비교하면, v1은 "폴리곤 연산은 레이어 조합당 딱 한 번(Minkowski 합 + Union)만 하고, 그 결과에 대해 점-내부 판정만 반복"하므로 훨씬 빠릅니다(점-내부 판정이 폴리곤 교차 계산보다 훨씬 가볍기 때문).
>
> **왜 v0와 "비트 단위로 완전히 동일"해야 하는가:** 이론적으로 두 방법은 같은 답을 내야 하지만, 부동소수점이 아니라 정수 연산이라 해도 "경계 접촉"처럼 미묘한 경우 구현 디테일(예: winding number 계산 순서, 자기교차 정리 방식)에 따라 답이 갈릴 위험이 있습니다. 그래서 실제로 40개 무작위 쌍 × 4개 인스턴스에 대해 **바이트 단위로 완전히 똑같은지**(`v0 == v1`) 강제 검증합니다 — "빠르게 바꿨는데 미묘하게 결과가 달라졌다"는 사고가 나중에 배치 판정 오류로 이어지면 훨씬 찾기 어려워지기 때문에, 지금 시점에 철저히 잡아둡니다.

`core/src/bindings.cpp`의 Core 클래스 바인딩에 테스트 전용 메서드 추가 (**캐시 우회** — `static_bm/entry_bm`을 거치지 않고 매번 새로 빌드):

```cpp

                       const std::string& kind, const std::string& method) {

                                           /*entry_kind=*/kind == "entry",
```

```python
"""해 상태 관리: placements 리스트가 유일한 정본. Core 반영 + 증분 목적함수 + 롤백."""
import math

Placement = tuple  # (block, bay, x, y, orient, entry, exit)


def _bbox(shape):
    pts = [p for layer in shape["layers"] for p in layer]
    xs = [p[0] for p in pts]; ys = [p[1] for p in pts]
    return (min(xs), min(ys), max(xs), max(ys))


class OpContext:
    """prob_info에서 파생되는 불변 테이블. Core에 없는 데이터(workload, pref, bbox)의 유일 출처."""

    def __init__(self, prob):
        self.prob = prob
        w = prob.get("weights", {})
        self.w1 = float(w.get("w1", 1.0))
        self.w2 = float(w.get("w2", 1.0))
        self.w3 = float(w.get("w3", 1.0))
        bl = prob["blocks"]
        self.n_blocks = len(bl)
        self.release = [b["release_time"] for b in bl]
        self.due = [b["due_date"] for b in bl]
        self.proc = [b["processing_time"] for b in bl]
        self.workload = [float(b["workload"]) for b in bl]
        self.pref = [b["bay_preferences"] for b in bl]
        self.smax = [max(b["bay_preferences"]) for b in bl]
        bays = prob["bays"]
        self.n_bays = len(bays)
        self.bay_w = [b["width"] for b in bays]
        self.bay_h = [b["height"] for b in bays]
        areas = [b["width"] * b["height"] for b in bays]
        avg = sum(areas) / len(areas)
        self.u = [avg / a for a in areas]
        self.horizon = max(self.due)                 # 시간 정규화 기준 H
        self.horizon_search = max(self.due) * 3      # 삽입 탐색 상한 (1주차 decoder와 동일)
        self.bbox = [[_bbox(s) for s in b["shape"]] for b in bl]           # [blk][orient]
        self.center = [[((mn_x + mx_x) / 2.0, (mn_y + mx_y) / 2.0)
                        for (mn_x, mn_y, mx_x, mx_y) in per_blk]
                       for per_blk in self.bbox]                            # [blk][orient]
        self.diag = max((w_ * w_ + h_ * h_) ** 0.5
                        for w_, h_ in zip(self.bay_w, self.bay_h))


class SolutionState:
    def __init__(self, core, ctx, placements):
        self.core, self.ctx = core, ctx
        core.clear()
        n = core.load_placements(list(placements))
        assert n == len(placements), f"incumbent 적재 실패: {n}/{len(placements)}"
        self.placed = {p[0]: tuple(p) for p in placements}
        self._z1 = sum(max(0, p[6] - ctx.due[p[0]]) for p in placements)
        self._loads = [0.0] * ctx.n_bays
        for p in placements:
            self._loads[p[1]] += ctx.workload[p[0]]
        self._z3 = sum(ctx.smax[p[0]] - ctx.pref[p[0]][p[1]] for p in placements)

    # -- 증분 장부 ---------------------------------------------------------
    def remove_block(self, blk):
        p = self.placed.pop(blk)
        self.core.remove(blk)
        c = self.ctx
        self._z1 -= max(0, p[6] - c.due[blk])
        self._loads[p[1]] -= c.workload[blk]
        self._z3 -= c.smax[blk] - c.pref[blk][p[1]]
        return p

    def place_block(self, p):
        if not self.core.place(*p):
            return False
        blk = p[0]
        self.placed[blk] = tuple(p)
        c = self.ctx
        self._z1 += max(0, p[6] - c.due[blk])
        self._loads[p[1]] += c.workload[blk]
        self._z3 += c.smax[blk] - c.pref[blk][p[1]]
        return True

    # -- 목적함수 (utils 수식 그대로) ---------------------------------------
    def _z2_of(self, loads):
        if self.ctx.n_bays < 2:
            return 0.0
        vals = [self.ctx.u[j] * loads[j] for j in range(self.ctx.n_bays)]
        return float(math.floor(max(vals) - min(vals)))   # max pair |a-b| == max-min

    def z2(self):
        return self._z2_of(self._loads)

    def z2_with(self, bay, dw):
        loads = list(self._loads)
        loads[bay] += dw
        return self._z2_of(loads)

    def z(self):
        return (float(self._z1), self.z2(), float(self._z3))

    def objective(self):
        z1, z2, z3 = self.z()
        return self.ctx.w1 * z1 + self.ctx.w2 * z2 + self.ctx.w3 * z3

    # -- 롤백 ---------------------------------------------------------------
    def snapshot(self):
        return dict(self.placed)

    def restore(self, snap):
        # feasible 집합의 부분집합은 feasible(전 제약이 unary/pairwise) → 재배치는 순서 무관 성공
        for blk in list(self.placed):
            if self.placed[blk] != snap.get(blk):
                self.remove_block(blk)
        for blk, p in snap.items():
            if blk not in self.placed:
                ok = self.place_block(p)
                assert ok, f"restore 실패: block {blk} 재배치 거부"

    def placements(self):
        return [self.placed[b] for b in sorted(self.placed)]
```

> 💡 **설명 — `OpContext`는 "Core가 모르는 것들을 담아두는 사전(dictionary)"입니다.** 1주차 `Core`(C++ 쪽)는 기하·시간 판정에 필요한 것만 알고 있고, `workload`(Z2 계산용), `bay_preferences`(Z3 계산용), 폴리곤의 bbox·중심점(Shaw 관련도 계산용, Task 3) 같은 정보는 원래 `prob_info` JSON에만 있습니다. `OpContext`는 이런 값들을 **한 번만 미리 계산해 리스트로 뽑아두는 캐시**입니다 — 매번 딕셔너리를 뒤져 `prob["blocks"][i]["workload"]`를 찾는 대신 `ctx.workload[i]`로 바로 접근하게 해서, 이후 수천~수만 번 반복될 ALNS 루프에서 자잘한 조회 비용을 줄입니다. "생성자에서 한 번에 다 계산해두고, 이후로는 절대 안 바뀌는(불변) 테이블"이라는 게 핵심입니다.
>
> **`SolutionState.__init__`의 증분 장부 초기화**: `_z1`(총 지각시간 누적값), `_loads`(bay별 워크로드 배열), `_z3`(선호도 손실 누적값)를 생성 시점에 딱 한 번 전체 스캔으로 계산해두고, 이후 `remove_block`/`place_block`은 **그 블록 하나 때문에 바뀐 만큼만 더하고 뺍니다**. 이게 Architecture 문단에서 말한 "증분 평가"의 실제 구현입니다. 특히 `_z1`, `_z3`는 "블록별로 독립적으로 더해지는 합"이라 증분이 정확히 O(1)로 끝나지만, `Z2`(`_z2_of`)는 "부하 배열 전체의 최대-최소"라서 매번 `n_bays`개 값을 다시 훑어야 합니다(다만 bay 개수가 적어 사실상 상수 시간).
>
> **`_z2_of`의 `max(vals) - min(vals)`가 원래 정의인 "최대 쌍별 절댓값 차이"와 같은 이유**: utils의 Z2 정의는 "모든 bay 쌍 `(j1, j2)`에 대해 `|u_j1·load_j1 - u_j2·load_j2|`의 최댓값"입니다. 그런데 실수 값들의 집합에서 "두 원소 차이의 절댓값의 최댓값"은 항상 "**가장 큰 값 − 가장 작은 값**"과 같습니다(둘 사이에 있는 어떤 값도 이 차이보다 크게 벌어질 수 없으므로) — 그래서 `O(n_bays²)`으로 모든 쌍을 비교할 필요 없이 `max - min` 한 번으로 끝낼 수 있습니다. 이건 목적함수 자체의 수학적 성질을 이용한 최적화이지, 근사가 아니라 **정확히 같은 값**입니다.
>
> **`z2_with(bay, dw)`가 "what-if 계산"인 이유**: `list(self._loads)`로 **복사본**을 만들어 그 복사본에만 `dw`를 더한 뒤 `_z2_of`를 계산합니다. 원본 `self._loads`는 전혀 건드리지 않으므로, "만약 이 블록을 이 bay에 넣는다면 Z2가 얼마가 될까"를 실제로 넣지 않고도 안전하게 미리 알아볼 수 있습니다 — 위 계약 절에서 예고한 "what-if 비용 평가" 패턴이 바로 이렇게 구현됩니다.
>
> **`restore`의 구현이 "diff 기반"인 이유**: snapshot과 현재 상태를 통째로 비교해서 "달라진 블록"만 골라 제거/재배치합니다(`self.placed[blk] != snap.get(blk)`). 전체를 지우고 처음부터 다시 놓는 것보다, 실제로 바뀐 것만 건드리는 게 더 적은 Core 호출로 끝나 빠릅니다. 주석에 있는 **"feasible 집합의 부분집합은 feasible"**이라는 근거가 왜 이 restore가 항상 성공한다고 믿을 수 있는지의 이유입니다 — 배치 제약은 전부 "블록 쌍 사이의 관계"(pairwise)이거나 "블록 하나만의 조건"(unary, bay 경계 등)이라서, 이미 feasible했던 배치 집합에서 일부를 골라 다시 놓아도(순서를 바꿔도) 여전히 feasible합니다. 그래서 `assert ok`로 "혹시 실패하면 그건 우리가 모르는 버그"라고 강하게 단언할 수 있습니다.

```python
"""파괴 연산자 6종 (설계서 §4 L3 표). 모두 (state, q, rng, ctx) -> list[removed block id]."""


def destroy_random(state, q, rng, ctx):
    ids = sorted(state.placed)
    out = rng.sample(ids, min(q, len(ids)))
    for b in out:
        state.remove_block(b)
    return out


def destroy_worst_tardiness(state, q, rng, ctx, p=3):
    """지각 기여 상위 블록을 rand^p 편향으로 제거. 지각 블록 부족분은 무작위 보충."""
    scored = sorted(((max(0, pl[6] - ctx.due[b]), b) for b, pl in state.placed.items()),
                    reverse=True)
    tardy = [b for t, b in scored if t > 0]
    rest = [b for t, b in scored if t == 0]
    out = []
    while tardy and len(out) < q:
        i = min(int(rng.random() ** p * len(tardy)), len(tardy) - 1)
        out.append(tardy.pop(i))
    while rest and len(out) < q:
        out.append(rest.pop(rng.randrange(len(rest))))
    for b in out:
        state.remove_block(b)
    return out


def relatedness(ctx, pi, pj, A, B, C):
    """Shaw 관련도: 작을수록 관련 깊음. A·d + B·|Δentry| + C·|Δexit|."""
    if pi[1] != pj[1]:
        d = 1.0                                   # 다른 bay = 공간 최대 거리로 간주
    else:
        ci = ctx.center[pi[0]][pi[4]]
        cj = ctx.center[pj[0]][pj[4]]
        dx = (pi[2] + ci[0]) - (pj[2] + cj[0])
        dy = (pi[3] + ci[1]) - (pj[3] + cj[1])
        d = (dx * dx + dy * dy) ** 0.5 / ctx.diag
    H = float(ctx.horizon)
    return A * d + B * abs(pi[5] - pj[5]) / H + C * abs(pi[6] - pj[6]) / H


def destroy_shaw(state, q, rng, ctx, A=0.55, B=1.36, C=0.89, p=6):
    ids = sorted(state.placed)
    snaps = {b: state.placed[b] for b in ids}     # 제거 전 위치 보존 (관련도 계산용)
    seed = ids[rng.randrange(len(ids))]
    removed = [seed]
    state.remove_block(seed)
    while len(removed) < min(q, len(ids)):
        r = removed[rng.randrange(len(removed))]
        rest = [b for b in ids if b in state.placed]
        rest.sort(key=lambda b: relatedness(ctx, snaps[r], snaps[b], A, B, C))
        pick = rest[min(int(rng.random() ** p * len(rest)), len(rest) - 1)]
        removed.append(pick)
        state.remove_block(pick)
    return removed
```

> 💡 **설명 — `rand^p` 편향 선택, ALNS에서 아주 자주 나오는 트릭입니다.** `worst_tardiness`와 `shaw` 둘 다 "완전히 결정적으로 1등만 뽑기"도 아니고 "완전 무작위"도 아닌 **중간 지점**을 원합니다(항상 1등만 뽑으면 매 반복이 판박이가 되어 다양성이 없고, 완전 무작위면 "지각이 심한 블록 우선"이라는 의도 자체가 사라지기 때문). 이를 위해 `rng.random() ** p`(0~1 사이 난수를 p제곱)를 인덱스로 씁니다.
> - `rng.random()`은 0~1 사이 균등분포 난수입니다. 이 값을 제곱(p번)하면, **원래 0.5였을 값이 `0.5^6 ≈ 0.016`처럼 훨씬 0에 가깝게 쏠립니다** — p가 클수록 "작은 값(=정렬 리스트의 앞쪽, 즉 가장 지각이 심하거나 가장 관련도가 높은 후보)"이 뽑힐 확률이 기하급수적으로 높아집니다.
> - `int(rng.random()**p * len(list))`로 이 쏠린 값을 리스트 길이에 곱해 정수 인덱스로 변환하면, "리스트 앞쪽일수록 자주 뽑히지만 뒤쪽도 가끔 뽑히는" 확률적 순위 기반 선택이 완성됩니다.
> - `worst_tardiness`는 p=3, `shaw`는 p=6을 씁니다 — p가 클수록 "진짜 상위권"에 더 강하게 쏠립니다. 이건 1주차에서 본 "biased randomization"(기하분포 편향)과 **철학은 완전히 같지만 구현 방식이 다른 자매 기법**입니다 — 둘 다 "그럴듯한 순서를 대체로 따르되 확률적으로 흔든다"는 목적을 위한 것으로, 기하분포 대신 거듭제곱 변환을 쓴 변형입니다.
>
> **`relatedness`(Shaw 관련도) 공식 뜯어보기**: `A·d + B·|Δentry|/H + C·|Δexit|/H`에서
> - `d`(공간 거리, 0~1로 정규화): 같은 bay 안에 있으면 두 블록의 "중심점"(bbox 중심, `ctx.center`) 사이 유클리드 거리를 bay 대각선 길이(`ctx.diag`)로 나눠 0~1 범위로 맞춥니다. **다른 bay에 있으면 아예 공간적으로 무관하다고 보고 최댓값(1.0)을 줍니다.**
> - `|Δentry|`, `|Δexit|`(시간 근접도, 역시 `H`=전체 horizon으로 정규화): 두 블록의 진입/퇴출 시각이 비슷할수록 "시간적으로 관련 있다"고 봅니다.
> - `A, B, C`(가중치 0.55/1.36/0.89)는 "공간 vs 진입시각 vs 퇴출시각 중 어느 근접성을 더 중요하게 볼지"를 조절하는 계수입니다. 설계서에 명시된 BAP(Berth Allocation Problem) 문헌의 튜닝값을 그대로 가져왔습니다(0.5절/설계서 참고문헌: Martín-Iradi et al. 2024).
> - **값이 작을수록(0에 가까울수록) "더 관련 있다"**는 것이 이 함수의 규약입니다(멀리 떨어지고 시간도 안 겹치면 값이 커짐) — `destroy_shaw`가 "관련도 오름차순 정렬 후 앞쪽(=관련도 낮은 값=더 관련 있는 블록)을 rand^p로 뽑는" 구조와 정확히 맞물립니다.
>
> **`destroy_shaw`의 절차**: (1) 아무 블록이나 하나(`seed`)를 무작위로 뽑아 제거합니다. (2) 이미 제거한 블록들 중 하나(`r`)를 무작위로 골라, **아직 안 뽑힌 나머지 블록들을 `r`과의 관련도 순으로 정렬**한 뒤 rand^p로 하나를 뽑아 제거 목록에 추가합니다. (3) 목표 개수(q)에 닿을 때까지 반복합니다. 이렇게 "이미 뽑은 것 중 아무거나와 관련 있는 걸 계속 물어오는" 방식이라, 결과적으로 **서로 얽혀있는 블록들의 군집(cluster)**이 통째로 제거됩니다 — 0.3절에서 예고한 "서로 얽혀있는 덩어리를 통째로 뜯는다"는 직관이 정확히 이렇게 구현됩니다.
>
> **`destroy_worst_tardiness`의 보충 로직**: 만약 지각 블록 수가 목표 제거량(q)보다 적으면(지각이 별로 없는 좋은 해), 지각이 아예 없는 블록들(`rest`) 중에서 **완전 무작위로** 나머지를 채웁니다 — "지각 블록만으로는 부족한데, 어차피 지각 없는 블록들 사이에는 우선순위를 매길 근거가 없으니" 무작위가 합리적인 선택입니다.

```python
def _median(xs):
    s = sorted(xs)
    return s[len(s) // 2]


def destroy_time_slice(state, q, rng, ctx):
    """한 bay의 시간창 [t0, t0+W)와 체류가 교차하는 블록 전부 제거 (시간 슬라이스 해방).
    last_window: 테스트 관측용 (bay, t0, W). 폴백 시 None."""
    destroy_time_slice.last_window = None
    bay = rng.randrange(ctx.n_bays)
    in_bay = [p for p in state.placed.values() if p[1] == bay]
    if not in_bay:
        return destroy_random(state, q, rng, ctx)
    t0 = rng.randrange(0, max(1, ctx.horizon))
    W = max(2, 2 * _median([ctx.proc[p[0]] for p in in_bay]))
    hits = []
    while True:
        hits = [p for p in in_bay if p[5] < t0 + W and p[6] > t0]
        if len(hits) >= max(2, q // 2) or W > 2 * ctx.horizon:
            break
        W = int(W * 1.5) + 1
    if len(hits) < 2:
        return destroy_random(state, q, rng, ctx)
    center = t0 + W / 2.0
    hits.sort(key=lambda p: abs((p[5] + p[6]) / 2.0 - center))
    out = [p[0] for p in hits[:q]]
    for b in out:
        state.remove_block(b)
    destroy_time_slice.last_window = (bay, t0, W)
    return out

def destroy_blocking_set(state, q, rng, ctx, max_probe=10):
    """지각 블록의 '조기 진입(entry ≤ due−P)'을 막는 방해 집합을 제거-탐침으로 역추적 제거.
    공간 선점자든 스윕 차단자든 '그 블록을 빼면 earliest_feasible이 당겨진다'로 동일하게 검출됨."""
    core = state.core

    def best_entry(blk, target):
        best = _BIG
        for bay in range(ctx.n_bays):
            for o in range(core.num_orients(blk)):
                hit = core.earliest_feasible(blk, bay, o, ctx.release[blk], target)
                if hit is not None:
                    best = min(best, hit[0])
        return best                                  # _BIG이면 target까지 진입 불가

    scored = sorted(((max(0, p[6] - ctx.due[b]), b) for b, p in state.placed.items()),
                    reverse=True)
    tardy = [b for t, b in scored if t > 0]
    if not tardy:
        return destroy_random(state, q, rng, ctx)

    removed = []
    for blk in tardy:
        if len(removed) >= q or blk not in state.placed:
            continue
        target = ctx.due[blk] - ctx.proc[blk]
        if target < ctx.release[blk]:
            continue                                 # zero-slack 이하: 조기 진입 자체가 불가
        p_blk = state.remove_block(blk)
        removed.append(blk)
        probes = 0
        while best_entry(blk, target) >= _BIG and len(removed) < q and probes < max_probe:
            cands = [p for p in state.placed.values()
                     if p[1] == p_blk[1]
                     and p[5] < target + ctx.proc[blk] and p[6] > ctx.release[blk]]
            if not cands:
                break
            cands.sort(key=lambda p: abs(p[2] - p_blk[2]) + abs(p[3] - p_blk[3]))
            base = best_entry(blk, target)
            best_gain, best_c = 0, None
            for p in cands[:max_probe]:
                pc = state.remove_block(p[0])
                e2 = best_entry(blk, target)
                assert state.place_block(pc)         # 원위치 복귀는 항상 성공(부분집합 feasible)
                probes += 1
                if base - e2 > best_gain:
                    best_gain, best_c = base - e2, p[0]
            victim = best_c if best_c is not None else cands[0][0]
            state.remove_block(victim)
            removed.append(victim)
    # q 미달 시 무작위 보충 (repair에 일감 보장)
    ids = sorted(state.placed)
    while ids and len(removed) < q:
        b = ids.pop(rng.randrange(len(ids)))
        state.remove_block(b)
        removed.append(b)
    return removed


DESTROY_NAMES = ["random", "worst_tardiness", "shaw",
                 "time_slice", "spatial_column", "blocking_set"]
```

> 💡 **설명 — `time_slice`와 `spatial_column`은 "시간/공간 중 한 축을 통째로 비운다"는 쌍둥이 아이디어입니다.**
> - `destroy_time_slice`: 무작위로 bay 하나를 고르고, 그 bay 안에서 폭 `W`짜리 시간창 `[t0, t0+W)`를 정한 뒤, **그 시간대와 체류기간이 겹치는 블록을 전부** 제거 후보로 봅니다. `W`의 초기값은 "그 bay에 있는 블록들의 처리시간 중앙값(median)의 2배"로 잡고(대략 블록 2~3개가 겹칠 정도), 걸리는 블록 수가 목표(`q//2`)에 못 미치면 창을 1.5배씩 넓혀가며 재시도합니다. 이렇게 찾은 후보 중에서도 "창의 중심에 가까운 것부터" q개를 최종 제거합니다 — "이 시간대, 이 구역을 통째로 밀어버리고 다시 채워 넣는다"는 그림입니다.
> - `destroy_spatial_column`: 방식은 거의 동일하되 축이 다릅니다. 시간이 아니라 **x좌표 구간**("기둥", column)을 정해서, 그 구간에 걸쳐 있는 블록을(체류 시간과 무관하게, 즉 언제 있었든) 제거합니다. bay 너비의 25%를 시작 폭으로 잡고 마찬가지로 부족하면 넓혀갑니다.
> - 두 함수 모두 "해당 bay에 블록이 아예 없으면"(`in_bay`가 빔) 또는 "창/스트립을 아무리 넓혀도 후보가 2개 미만이면" `destroy_random`으로 **폴백**합니다 — 항상 뭔가는 제거해서 복구 단계에 일거리를 줘야 하기 때문입니다. 이때 `last_window`/`last_strip`이 `None`으로 남아 "이건 폴백 경로였다"는 것을 테스트가 구분할 수 있게 합니다(함수 자체에 속성을 붙이는 것은 파이썬에서 함수도 객체라 가능한 기법 — "마지막 호출 결과를 부작용으로 기록해두는" 디버깅/테스트용 흔한 트릭입니다).
>
> **`destroy_blocking_set`이 이 프로젝트에서 가장 "문제 특화적"인 이유**: 다른 5개 연산자는 "어디를 부술지"를 기하학적/통계적 기준(무작위, 지각량, 관련도, 시공간 구간)만으로 정하지만, 이 연산자는 **"왜 이 블록이 지각하는가"라는 인과관계를 직접 추적**합니다. 절차를 풀면:
> 1. 가장 지각이 심한 블록(`blk`)부터, "만약 지각 없이 넣으려면 몇 일에 들어와야 했는가"(`target = due - processing_time`)를 계산합니다.
> 2. `blk`를 일단 빼고(`state.remove_block`), "지금 상태에서 `blk`를 `target`일까지 넣을 수 있는 자리가 있는가"(`best_entry`)를 확인합니다.
> 3. **불가능하면(`>= _BIG`)**, 같은 bay에서 그 시간대에 걸쳐있는 다른 블록들을 후보로 놓고, **하나씩 빼봤다가 다시 넣어보며**(`pc = state.remove_block(...)`; `earliest_feasible` 재측정; `state.place_block(pc)`로 복귀) "이 블록을 빼면 `blk`가 얼마나 더 일찍 들어올 수 있게 되는지"(`base - e2`, gain)를 **직접 실험으로 측정**합니다.
> 4. gain이 가장 큰(=`blk`를 가장 심하게 막고 있는) 블록을 실제로 제거하고, 여전히 안 되면 이 탐침(probe)을 반복합니다(`max_probe`회 제한).
>
> 이 "빼봤다가 측정하고 다시 넣는" 방식은 **"파괴적이지 않은 실험"**입니다 — `assert state.place_block(pc)`로 항상 원위치 복귀가 보장되므로(부분집합이라 feasible 유지), 측정 자체는 최종 상태에 아무 영향을 주지 않고 순수하게 "이 블록의 영향력이 얼마나 큰지"를 재는 용도로만 씁니다. 이런 "제거해보고 효과를 재고 원상복구"하는 패턴은 민감도 분석(sensitivity analysis)의 발상과 비슷합니다. 마지막으로 `zero-slack` 체크(`target < release`)는 "애초에 물리적으로 지각 없이 넣는 게 불가능한 블록"(release_time 자체가 이미 늦어서 slack이 0 이하)은 아무리 방해 블록을 치워도 소용없으니 건너뛰는 조기 종료 조건입니다.

```python
"""복구 연산자. 후보 생성은 core.earliest_feasible/free_positions만 사용 (자체 기하 금지).
순서 결정은 1주차 priority.atc_order를 재사용한다."""
from solver.priority import atc_order


def insertion_cost(state, blk, bay, entry, ctx):
    """블록을 (bay, entry)에 넣을 때의 가중 목적 증가분: w1·지각 + w2·ΔZ2 + w3·pref 손실."""
    tard = max(0, entry + ctx.proc[blk] - ctx.due[blk])
    dz2 = state.z2_with(bay, ctx.workload[blk]) - state.z2()
    pref_loss = ctx.smax[blk] - ctx.pref[blk][bay]
    return ctx.w1 * tard + ctx.w2 * dz2 + ctx.w3 * pref_loss


def candidate_for_bay(state, blk, bay, ctx):
    """해당 bay에서의 최선 후보. bay 안에서는 비용이 entry에 단조 → 방향별 earliest의 min."""
    core = state.core
    best = None
    for o in range(core.num_orients(blk)):
        hit = core.earliest_feasible(blk, bay, o, ctx.release[blk], ctx.horizon_search)
        if hit is None:
            continue
        e, x, y = hit
        cand = (insertion_cost(state, blk, bay, e, ctx), bay, x, y, o, e)
        if best is None or cand < best:
            best = cand
    return best


def candidates_by_bay(state, blk, ctx):
    out = {}
    for bay in range(ctx.n_bays):
        c = candidate_for_bay(state, blk, bay, ctx)
        if c is not None:
            out[bay] = c
    return out


def _place_candidate(state, blk, cand, ctx):
    cost, bay, x, y, o, e = cand
    ok = state.place_block((blk, bay, x, y, o, e, e + ctx.proc[blk]))
    assert ok, f"조회 직후 배치 실패: block {blk} bay {bay} (상태 불변식 위반)"


def repair_greedy_noise(state, removed, rng, ctx, noise=0.1):
    """ATC biased-randomization 순서(디코더와 동일 기계장치) + 비용 곱셈 노이즈 U[1−η,1+η]."""
    rset = set(removed)
    order = [b for b in atc_order(ctx.prob, rng=rng) if b in rset]
    for blk in order:
        cands = candidates_by_bay(state, blk, ctx)
        if not cands:
            return False                     # 호출자(loop)가 snapshot으로 롤백
        best = min(cands.values(),
                   key=lambda c: (c[0] * (1.0 + rng.uniform(-noise, noise)), c[5], c[3], c[2]))
        _place_candidate(state, blk, best, ctx)
    return True
```

> 💡 **설명 — `insertion_cost`는 "이 블록을 여기에 넣으면 목적함수가 얼마나 늘어나는가"의 근사 추정치입니다.** 세 항을 더합니다: `w1·지각`(이 블록 자체의 지각시간 × Z1 가중치), `w2·ΔZ2`(이 bay에 워크로드를 더했을 때 Z2가 얼마나 늘어나는지 — 앞서 만든 `z2_with`의 "what-if" 계산을 그대로 사용), `w3·pref_loss`(이 bay가 최선호 bay가 아니라서 생기는 Z3 손실). 이 세 항을 utils와 동일한 가중치(`ctx.w1/w2/w3`)로 더해 "이 삽입 하나가 전체 objective를 얼마나 밀어올릴지"의 **근사값**을 얻습니다(다른 블록들과의 상호작용까지 완벽히 반영한 진짜 값은 아니지만, "지금 이 순간 기준"으로는 정확합니다).
>
> **왜 근사인가:** 예를 들어 이 블록을 넣은 뒤 다른 블록이 밀려서 발생하는 연쇄 효과까지는 계산하지 않습니다. 하지만 삽입 기반 휴리스틱에서는 "각 삽입 시점에서의 국소적 비용"만으로 충분히 실용적인 결과를 냅니다 — 정확한 전역 최적을 포기하고 계산 속도를 얻는 전형적인 휴리스틱 트레이드오프입니다.
>
> **`candidate_for_bay`의 주석 "bay 안에서는 비용이 entry에 단조 → 방향별 earliest의 min"의 의미:** 같은 bay 안에서는 "더 늦게 들어올수록(entry가 클수록) 지각이 늘거나 같아질 뿐, 줄어들지는 않는다"(단조, monotonic)는 성질이 있습니다. 그래서 각 방향(orient)에 대해 **"그 방향으로 가장 이르게 들어올 수 있는 시각"만 확인하면 충분**하고, 그보다 늦은 시각들을 따로 검토할 필요가 없습니다 — 탐색 공간을 줄이는 근거가 되는 성질입니다. 방향이 여러 개면 그중 비용이 가장 싼 것을 고릅니다.
>
> **`repair_greedy_noise`의 "노이즈"는 1주차 biased randomization과 다른 종류의 무작위성입니다.** 1주차 ATC의 biased randomization은 "블록을 처리하는 **순서**"를 흔들었다면, 여기 `noise`는 **순서는 ATC 그대로 따르되(`atc_order`를 그대로 재사용), 각 블록을 놓을 bay를 고를 때 비용에 곱셈 잡음**(`c[0] * (1.0 + rng.uniform(-noise, noise))`, 예: noise=0.1이면 비용을 90%~110% 사이로 무작위로 흔듦)을 줘서 "거의 최선이지만 가끔 다른 bay를 선택"하게 합니다. 즉 이 연산자 하나에 **두 겹의 무작위성**(순서 편향 + 비용 잡음)이 들어있는 셈입니다 — 두 종류를 겹쳐 쓰는 것도 ALNS/GRASP류 다양화 기법에서 흔합니다. tie-break로 `(cost*noise, entry, x, y)` 사전식 비교를 쓰는 것도 1주차 디코더의 관용구를 그대로 계승한 것입니다.

```python
def _regret_value(costs, k, M):
    """오름차순 비용 리스트의 regret-k. 대안 부족분은 M 가산으로 채운다."""
    costs = sorted(costs)
    while len(costs) < k:
        costs.append(costs[-1] + M)
    return sum(costs[l] - costs[0] for l in range(1, k))


def repair_regret(state, removed, rng, ctx, k=2):
    """regret-k 삽입. 기하 재탐색은 '방금 삽입된 bay'만, 비용 산술은 매회 전 bay 갱신.
    (배치 제약은 bay 내부 pairwise뿐이라 다른 bay 후보의 기하는 유효하게 유지됨.
     단 Z2 항은 전역이므로 비용만 재계산한다.)"""
    pending = set(removed)
    cand = {b: candidates_by_bay(state, b, ctx) for b in pending}
    M = ctx.w1 * float(ctx.horizon)
    while pending:
        best_blk, best_key = None, None
        for b in sorted(pending):
            if not cand[b]:
                return False
            regret = _regret_value([c[0] for c in cand[b].values()], k, M)
            key = (regret, -min(c[0] for c in cand[b].values()))   # 큰 regret, tie→작은 비용
            if best_key is None or key > best_key:
                best_key, best_blk = key, b
        chosen = min(cand[best_blk].values())
        _place_candidate(state, best_blk, chosen, ctx)
        pending.discard(best_blk)
        jbay = chosen[1]
        for b in pending:
            hit = candidate_for_bay(state, b, jbay, ctx)           # 기하 재탐색: jbay만
            if hit is None:
                cand[b].pop(jbay, None)
            else:
                cand[b][jbay] = hit
            for bay, c in list(cand[b].items()):                   # 비용 산술 갱신: 전 bay
                if bay == jbay:
                    continue
                cand[b][bay] = (insertion_cost(state, b, bay, c[5], ctx),
                                c[1], c[2], c[3], c[4], c[5])
    return True


def repair_most_constrained(state, removed, rng, ctx):
    """선택지 적은 블록부터: (지각 0 슬롯 수, 잔여 slack, −면적) 오름차순으로 최선 삽입."""
    core = state.core

    def zero_tard_options(blk):
        """지각 0으로 넣을 수 있는 (bay, orient) 슬롯 점수. 자유 위치가 넉넉한 슬롯은 2점,
        빡빡한 슬롯(자유 셀 ≤ 8)은 1점 — 점수 낮은 블록이 더 구속됨 → 먼저 삽입."""
        latest = ctx.due[blk] - ctx.proc[blk]
        if latest < ctx.release[blk]:
            return 0
        n = 0
        for bay in range(ctx.n_bays):
            for o in range(core.num_orients(blk)):
                hit = core.earliest_feasible(blk, bay, o, ctx.release[blk], latest)
                if hit is not None:
                    e, x, y = hit
                    free = len(core.free_positions(blk, bay, o, e, e + ctx.proc[blk]))
                    n += 2 if free > 8 else 1
        return n

    def area(blk):
        mn_x, mn_y, mx_x, mx_y = ctx.bbox[blk][0]
        return (mx_x - mn_x) * (mx_y - mn_y)

    order = sorted(removed,
                   key=lambda b: (zero_tard_options(b),
                                  ctx.due[b] - ctx.proc[b] - ctx.release[b],
                                  -area(b)))
    for blk in order:
        cands = candidates_by_bay(state, blk, ctx)
        if not cands:
            return False
        _place_candidate(state, blk, min(cands.values()), ctx)
    return True
```

> 💡 **설명 — `_regret_value`가 0.4절에서 예고한 regret-k 공식을 정확히 구현한 부분입니다.** `costs`(그 블록을 넣을 수 있는 bay별 비용들)를 오름차순 정렬한 뒤, `k`개까지의 "1등과의 차이"를 다 더합니다(`sum(costs[l] - costs[0] for l in range(1, k))`). k=2면 "2등−1등" 하나만, k=3이면 "2등−1등"과 "3등−1등"을 더합니다. **대안이 k개보다 적으면**(`while len(costs) < k`) 가짜 대안을 "가장 비싼 것 + M"으로 채워 넣어 강제로 리스트를 늘립니다 — 대안이 진짜 부족한 블록일수록 이 가짜 항이 regret 값을 크게 부풀려서, "선택의 여지가 없는 블록"이 최우선으로 처리되도록 유도합니다. 테스트 `test_regret_prefers_fewer_alternatives`가 정확히 이 성질("대안 1개 < 대안 2개인데 regret은 반대로 대안 1개 쪽이 더 큼")을 순수 산술로 검증합니다.
>
> **`repair_regret`의 메인 루프**: 매 반복마다 "아직 안 넣은 블록들" 중 **regret이 가장 큰 블록**을 하나 골라 그 블록의 1등 후보 bay에 확정 배치합니다. 배치 후에는 다른 대기 중인 블록들의 후보 정보를 갱신해야 하는데, 여기 최적화 포인트가 있습니다 — 주석에서 말하듯 **"기하 재탐색은 방금 채워진 bay만"** 다시 하고(그 bay 안의 여유 공간이 실제로 줄었으니), **"비용 산술은 전체 bay"**에 대해 재계산합니다(Z2가 전역 지표라 다른 bay를 골라도 워크로드 분포가 바뀌어 비용이 달라지기 때문 — 하지만 기하학적으로 그 bay에 자리가 있는지 없는지는 안 바뀌므로 다시 조회할 필요는 없습니다). 이건 "정확히 필요한 만큼만 다시 계산해서 속도를 아끼는" 흔한 성능 최적화입니다.
>
> **`repair_most_constrained`는 CSP(제약만족문제)의 MRV(Minimum Remaining Values) 휴리스틱과 같은 발상입니다.** "변수 할당 문제에서, 가능한 값의 개수가 가장 적은(가장 제약이 심한) 변수부터 먼저 정하라"는 원칙을 블록 배치에 적용한 것입니다. `zero_tard_options`가 "이 블록이 지각 0으로 들어갈 수 있는 슬롯이 얼마나 많은지"를 세는데, 단순히 개수만 세지 않고 **그 슬롯이 얼마나 여유로운지도 가중**합니다(`free_positions`로 실제 놓을 수 있는 좌표 수를 세어, 8개보다 많으면 2점, 적으면(빡빡하면) 1점). 이렇게 점수가 낮은(선택지 적고 빡빡한) 블록부터 먼저 확정하면, "선택지 많은 블록에게 자리를 뺏겨서 정작 선택지 없던 블록이 오도 가도 못하는" 상황을 예방할 수 있습니다. 동점이면 `slack`(여유시간)이 적은 순, 그다음 면적이 큰 순(1주차 ATC의 "동급이면 큰 블록 먼저"와 같은 타이브레이크 철학)으로 추가 정렬합니다.
>
> **regret-k와 most-constrained-first의 차이**: 둘 다 "어려운 블록을 먼저 처리"한다는 목표는 같지만, regret은 "**지금 당장 눈에 보이는 비용 격차**"(1등과 2등의 차이)로 다급함을 재는 반면, most-constrained는 "**애초에 넣을 수 있는 슬롯 개수 자체**"로 다급함을 잽니다. 서로 다른 각도에서 "다급한 블록을 먼저"라는 같은 목표에 접근하는 두 계열의 휴리스틱이라, 인스턴스 특성에 따라 어느 쪽이 더 잘 먹히는지가 달라질 수 있습니다 — 이게 바로 0.6절에서 예고한 ablation 실험(`--disable-op`)으로 실측해야 하는 이유입니다.

```python
"""수용 기준. RRT 기본(설계서 §4 L3: 초기 임계 2~5% 선형 감소), reheated SA 대안."""
import math


class RecordToRecord:
    def __init__(self, initial_obj, start_pct=0.03):
        self.thr0 = start_pct * initial_obj

    def accept(self, cand_obj, cur_obj, best_obj, progress, rng):
        thr = self.thr0 * (1.0 - min(max(progress, 0.0), 1.0))
        return cand_obj < best_obj + thr


class ReheatedSA:
    def __init__(self, initial_obj, start_pct=0.05, alpha=0.9995,
                 reheat_pct=0.5, min_ratio=1e-3):
        self.T0 = max(1e-9, start_pct * initial_obj)
        self.T = self.T0
        self.alpha = alpha
        self.reheat_pct = reheat_pct
        self.min_ratio = min_ratio
        self.reheats = 0

    def accept(self, cand_obj, cur_obj, best_obj, progress, rng):
        if cand_obj < cur_obj:
            ok = True
        else:
            ok = rng.random() < math.exp(-(cand_obj - cur_obj) / max(self.T, 1e-9))
        self.T *= self.alpha
        if self.T < self.T0 * self.min_ratio:          # 재가열: 매회 절반 높이로
            self.reheats += 1
            self.T = self.T0 * (self.reheat_pct ** self.reheats)
        return ok


def make_acceptance(cfg, initial_obj):
    if getattr(cfg, "acceptance", "rrt") == "sa":
        return ReheatedSA(initial_obj, start_pct=cfg.sa_start_pct)
    return RecordToRecord(initial_obj, start_pct=cfg.rrt_start_pct)
```

> 💡 **설명 — `ReheatedSA`의 `accept` 로직이 바로 시뮬레이티드 어닐링(담금질 기법)의 표준 공식(Metropolis criterion)입니다.**
> - `cand_obj < cur_obj`(candidate가 현재 해보다 좋음)면 **무조건 수용**합니다 — 개선은 항상 환영.
> - 그렇지 않으면(나빠짐) `exp(-(cand_obj - cur_obj) / T)`(볼츠만 인자)만큼의 확률로 수용합니다. `cand_obj - cur_obj`(악화 폭)가 작을수록, 또는 `T`(온도)가 높을수록 이 확률이 1에 가까워집니다(더 잘 받아줌). 반대로 온도가 낮아지면 웬만큼 나쁜 해는 다 거부하게 됩니다.
> - 매 호출마다 `self.T *= self.alpha`(예: 0.9995)로 온도를 아주 조금씩 낮춥니다(냉각, cooling schedule) — 이게 "탐색 초반엔 관대하게, 후반엔 깐깐하게"라는 RRT와 같은 철학을 확률적으로 구현한 것입니다.
> - **재가열(reheat)**: 온도가 초기값의 `min_ratio`(예: 0.1%) 아래로 완전히 식으면, 사실상 더 이상 나쁜 해를 받아주지 않는(=단순 언덕오르기와 다를 바 없는) 상태가 되어 탐색이 정체될 위험이 있습니다. 이때 온도를 `T0 × reheat_pct^reheats`로 **다시 끌어올려**(단, 재가열할 때마다 절반씩 낮게 — 무한정 다시 뜨거워지진 않음) 탐색에 다시 활력을 줍니다. 테스트에서 "alpha=0.5로 급격히 식힌 뒤 50회 반복하면 reheats가 1 이상 발생"하는 것으로 이 메커니즘을 확인합니다.
>
> **`make_acceptance`가 "덕 타이핑(duck typing)"으로 설계되었다는 점**: `getattr(cfg, "acceptance", "rrt")`는 "cfg가 정확히 어떤 클래스인지는 상관없고, `acceptance`라는 속성만 갖고 있으면 된다"는 파이썬 특유의 유연한 다형성 방식입니다. 실제로 테스트에서는 `AlnsConfig`가 아니라 즉석에서 만든 간단한 `class Cfg`를 넘겨도 잘 동작하는 것을 확인합니다 — "오리처럼 걷고 오리처럼 울면 오리로 취급한다"는 덕 타이핑의 정의 그대로입니다.

```python
"""연산자 선택. 기본은 정적 균등(설계서: 적응층 기여 ~0.14%라 연산자 품질에 집중),
--adaptive 시 세그먼트 100회·점수 33/13/9·반응 0.1의 룰렛휠."""


class OperatorSelector:
    def __init__(self, names, adaptive=False, segment=100, scores=(33, 13, 9), reaction=0.1):
        if not names:
            raise ValueError("OperatorSelector: 연산자 목록이 비었음 (disable_ops 과다?)")
        self.names = list(names)
        self.adaptive = adaptive
        self.segment = segment
        self.sigma = {"best": scores[0], "better": scores[1], "accepted": scores[2]}
        self.reaction = reaction
        self.w = {n: 1.0 for n in self.names}
        self._scores = {n: 0.0 for n in self.names}
        self._uses = {n: 0 for n in self.names}
        self._iter = 0
        self.total_uses = {n: 0 for n in self.names}

    def select(self, rng):
        if not self.adaptive:
            name = self.names[rng.randrange(len(self.names))]
        else:
            total = sum(self.w.values())
            r = rng.random() * total
            acc = 0.0
            name = self.names[-1]
            for n in self.names:
                acc += self.w[n]
                if r <= acc:
                    name = n
                    break
        self._uses[name] += 1
        self.total_uses[name] += 1
        return name

    def reward(self, name, kind):
        self._scores[name] += self.sigma[kind]

    def tick(self):
        self._iter += 1
        if self.adaptive and self._iter % self.segment == 0:
            for n in self.names:
                if self._uses[n] > 0:
                    self.w[n] = ((1.0 - self.reaction) * self.w[n]
                                 + self.reaction * (self._scores[n] / self._uses[n]))
                self._scores[n] = 0.0
                self._uses[n] = 0

    def stats(self):
        return {"weights": dict(self.w), "uses": dict(self.total_uses)}
```

> 💡 **설명 — `select`의 `adaptive=False`(기본) 분기는 그냥 "목록에서 균등 무작위로 하나 뽑기"입니다.** `adaptive=True`일 때만 **룰렛휠 선택(roulette wheel selection)**을 씁니다: 각 연산자의 가중치(`w[n]`)를 다 더한 총합(`total`)만큼의 구간을 그리고, 그 구간 안에서 무작위 점(`r`)을 찍은 뒤 "각 연산자가 차지한 몫(누적 가중치 `acc`)에 그 점이 들어가는 첫 연산자"를 고릅니다. 가중치가 큰 연산자일수록 구간이 넓어 뽑힐 확률이 높아지는, 유전 알고리즘(GA)에서 부모 개체를 뽑을 때 쓰는 것과 똑같은 방식입니다.
>
> **`tick()`의 세그먼트 갱신식이 적응 가중치의 핵심입니다.** "세그먼트"란 반복 100회 단위의 구간을 말합니다(`segment=100`). 100회가 지날 때마다(`self._iter % self.segment == 0`), 그 구간 동안 각 연산자가 쓰인 횟수(`_uses`)와 획득한 점수(`_scores`, `reward`로 누적됨)를 가지고 가중치를 다음처럼 갱신합니다:
> `w[n] ← (1 − reaction)·w[n] + reaction·(그 구간 평균 점수)`
> 이건 **지수이동평균(exponential moving average, EMA)**의 한 형태입니다 — "예전 가중치를 대부분(90%, `1-reaction`) 유지하되, 최근 성과(10%, `reaction`)를 살짝 반영해 서서히 조정"하는 방식으로, 한 번의 우연한 성과에 가중치가 과민 반응하지 않도록(완만하게 수렴하도록) 막아줍니다. 테스트의 주석 `0.9 + 3.3 = 4.2`가 이 공식을 정확히 손으로 계산해 검증한 것입니다(reaction=0.1이니 `1-reaction=0.9`, `good`이 매번 33점을 받고 매번 뽑혔다고 가정하면 평균 점수도 33).
> **`reward`의 `kind` 인자**(계약 절에서 예고한 `"best"/"better"/"accepted"`)에 따라 `sigma`(σ=33/13/9) 중 하나가 점수로 더해집니다 — "최고 기록 경신"에 가장 큰 점수(33)를, "그냥 받아들여짐"에 가장 작은 점수(9)를 주는 차등 보상 체계입니다.
>
> **왜 기본값이 정적(균등)인가:** 주석과 설계서(0.5절에서 언급한 Turkeš et al. 2021 메타분석)가 근거입니다 — 적응층이 실제 성능에 기여하는 정도가 통계적으로 미미(~0.14%)하다는 문헌 결과가 있어서, 이 프로젝트는 "복잡한 적응 로직에 시간을 쓰기보다, 연산자 자체의 품질(파괴 6종·복구 4종을 잘 설계하는 것)에 공수를 집중"하기로 결정했습니다. `--adaptive` 플래그는 "혹시 몰라 만들어는 두되, 기본은 끈다"는 보수적인 설계 선택입니다.

```python
"""ALNS 본체. 항상-실행가능 불변식: 완성해만 수용/기록, 실패·거부는 snapshot 롤백."""
import random
import time
from dataclasses import dataclass
from functools import partial

from solver.alns.state import OpContext, SolutionState
from solver.alns import destroy as D
from solver.alns import repair as R
from solver.alns.accept import make_acceptance
from solver.alns.weights import OperatorSelector


@dataclass
class AlnsConfig:
    enabled: bool = True
    removal_rate: float = 0.33            # 설계서: 20~35%, 기본 0.33
    acceptance: str = "rrt"               # "rrt" | "sa"
    rrt_start_pct: float = 0.03           # 초기 임계 = 3% of initial obj (2~5% 범위)
    sa_start_pct: float = 0.05
    adaptive: bool = False                # 기본: 정적 균등
    segment: int = 100
    scores: tuple = (33, 13, 9)
    reaction: float = 0.1
    shaw_weights: tuple = (0.55, 1.36, 0.89)
    shaw_p: int = 6
    noise: float = 0.1
    disable_ops: tuple = ()               # 파괴/복구 공용 이름공간 (ablation용)
    max_iters: int | None = None          # 테스트/프로파일용 상한 (None=예산까지)
    seed: int = 0                         # shell이 improve rng 파생에 사용 (재현성)


def _build_ops(cfg):
    A, B, C = cfg.shaw_weights
    d = {
        "random": D.destroy_random,
        "worst_tardiness": D.destroy_worst_tardiness,
        "shaw": partial(D.destroy_shaw, A=A, B=B, C=C, p=cfg.shaw_p),
        "time_slice": D.destroy_time_slice,
        "spatial_column": D.destroy_spatial_column,
        "blocking_set": D.destroy_blocking_set,
    }
    r = {
        "greedy_noise": partial(R.repair_greedy_noise, noise=cfg.noise),
        "regret2": partial(R.repair_regret, k=2),
        "regret3": partial(R.repair_regret, k=3),
        "most_constrained": R.repair_most_constrained,
    }
    dsel = {k: v for k, v in d.items() if k not in cfg.disable_ops}
    rsel = {k: v for k, v in r.items() if k not in cfg.disable_ops}
    if not dsel or not rsel:
        raise ValueError(f"disable_ops={cfg.disable_ops}: 파괴/복구 연산자가 남지 않음")
    return dsel, rsel


def improve(core, incumbent, budget, *, prob, rng=None, cfg=None, trace=None, stats=None):
    cfg = cfg or AlnsConfig()
    if not cfg.enabled or not incumbent:
        return list(incumbent)
    rng = rng or random.Random(0)
    dops, rops = _build_ops(cfg)

    ctx = OpContext(prob)
    state = SolutionState(core, ctx, incumbent)
    n = len(incumbent)
    best = state.placements()
    best_obj = state.objective()
    cur_obj = best_obj
    acc = make_acceptance(cfg, best_obj)
    dsel = OperatorSelector(list(dops), cfg.adaptive, cfg.segment, cfg.scores, cfg.reaction)
    rsel = OperatorSelector(list(rops), cfg.adaptive, cfg.segment, cfg.scores, cfg.reaction)

    t0 = time.monotonic()
    total = max(budget.remain(), 1e-9)     # improve 진입 시점의 잔여 예산 = progress 분모
    it = 0
    if trace is not None:
        trace.append((0.0, best_obj))
    q = max(2, round(cfg.removal_rate * n))

    while not budget.expired() and (cfg.max_iters is None or it < cfg.max_iters):
        it += 1
        snap = state.snapshot()
        dname = dsel.select(rng)
        rname = rsel.select(rng)
        try:
            removed = dops[dname](state, q, rng, ctx)
            ok = rops[rname](state, removed, rng, ctx)
        except AssertionError:
            state.restore(snap)            # 방어: 어떤 연산자 이상도 incumbent 불변식 유지
            dsel.tick(); rsel.tick()
            continue
        if ok and len(state.placed) == n:
            cand_obj = state.objective()
            progress = min(1.0, (time.monotonic() - t0) / total)
            if cand_obj < best_obj - 1e-9:
                best, best_obj, cur_obj = state.placements(), cand_obj, cand_obj
                dsel.reward(dname, "best"); rsel.reward(rname, "best")
                if trace is not None:
                    trace.append((time.monotonic() - t0, best_obj))
            elif acc.accept(cand_obj, cur_obj, best_obj, progress, rng):
                kind = "better" if cand_obj < cur_obj - 1e-9 else "accepted"
                dsel.reward(dname, kind); rsel.reward(rname, kind)
                cur_obj = cand_obj
            else:
                state.restore(snap)        # 거부 → current 유지
        else:
            state.restore(snap)            # 복구 실패 → 롤백 (항상-실행가능)
        dsel.tick(); rsel.tick()

    if stats is not None:
        stats.update({"iters": it, "best_obj": best_obj,
                      "destroy": dsel.stats(), "repair": rsel.stats()})
    return best
```

> 💡 **설명 — 이 `improve()` 함수가 지금까지 만든 6개 조각(state/destroy/repair/accept/weights)을 전부 이어 붙이는 지점입니다.** 코드를 흐름대로 읽으면:
>
> **준비 단계**: `_build_ops(cfg)`로 "이번 실행에서 쓸 파괴/복구 연산자 딕셔너리"를 만듭니다(`disable_ops`에 있는 이름은 빼고). `partial(D.destroy_shaw, A=A, B=B, C=C, p=cfg.shaw_p)`처럼 **`functools.partial`**을 쓰는 이유: `destroy_shaw`는 원래 `A, B, C, p`라는 추가 인자를 받는데, `loop.py`가 실제로 호출할 때는 다른 연산자들과 **똑같은 시그니처**(`state, q, rng, ctx`)로 통일해서 부르고 싶습니다. `partial`은 "함수에 일부 인자를 미리 박아 넣어, 남은 인자만 받는 새 함수를 만드는" 파이썬 표준 기법입니다 — 이렇게 하면 `dops[dname](state, q, rng, ctx)`처럼 **어떤 연산자든 같은 방식으로 호출**할 수 있어, 루프 코드가 "지금 고른 게 shaw인지 random인지" 신경 쓸 필요가 없어집니다(정책과 실행을 분리하는 전형적 패턴).
> `if not dsel or not rsel: raise ValueError(...)`는 0.6절에서 예고한 "복구 연산자를 전부 꺼버리면 아무것도 할 수 없다"는 상황을 미리 막는 방어 코드입니다(Task 13의 `test_all_repair_disabled_raises`가 이걸 검증).
>
> **메인 루프의 한 반복(iteration)이 정확히 ALNS의 정의 그대로입니다**:
> 1. `snap = state.snapshot()` — 되돌릴 수 있게 지금 상태를 저장(롤백 대비).
> 2. `dsel.select(rng)` / `rsel.select(rng)` — 이번 반복에 쓸 파괴/복구 연산자를 하나씩 고름(정적이면 균등무작위, 적응이면 룰렛휠 — Task 8).
> 3. `dops[dname](...)` — 고른 파괴 연산자 실행(Task 3·4) → `removed`(제거된 블록 id들).
> 4. `rops[rname](...)` — 고른 복구 연산자 실행(Task 5·6) → 성공하면 완전해, 실패하면 `ok=False`.
> 5. 성공(`ok and len(state.placed)==n`)이면 결과 objective를 계산해 세 갈래로 나눕니다:
>    - **최고 기록 경신**(`cand_obj < best_obj`): 즉시 채택 + 최고 보상(`"best"`) 지급 + trace 기록.
>    - **기록 경신은 아니지만 수용 기준(RRT/SA)이 받아줌**: 현재 해로 채택(`cur_obj` 갱신) + 보상(`"better"` 또는 `"accepted"`).
>    - **수용 기준도 거부**: `state.restore(snap)`으로 원상복구, 이번 시도는 없던 일이 됨.
> 6. 복구 자체가 실패(`ok=False`)했거나 예외(`AssertionError`)가 났으면 **무조건 롤백**합니다.
> 7. `dsel.tick()`/`rsel.tick()`으로 선택기의 내부 카운터를 한 칸 전진시킵니다(적응 모드면 100회마다 가중치 갱신, Task 8).
>
> **"항상-실행가능(always-feasible) 불변식"이 코드 곳곳의 `restore` 호출로 보장됩니다.** 파괴-복구 시도가 실패하든, 예외가 나든, 수용 기준이 거부하든 — **어떤 경우에도 결국 `state.restore(snap)`으로 시도 이전 상태로 돌아갑니다.** 그래서 이 루프는 "밑져야 본전"으로, 시도했다가 잘 안 되면 그냥 이전 상태 그대로 다음 반복으로 넘어갈 뿐입니다. 이게 Global Constraints에서 강조한 "ALNS의 어떤 예외도 incumbent를 파괴하면 안 된다"를 실현하는 구체적 코드입니다.
>
> **`progress`(예산 소진율)가 어떻게 계산되는지**: `(time.monotonic() - t0) / total`. `t0`는 `improve()`가 시작된 시각, `total`은 "이 함수가 시작될 때 남아있던 전체 예산"(`budget.remain()`)입니다. 이 비율이 RRT의 임계값 선형 감소, SA의 진행 정도 판단에 쓰입니다 — "시간이 얼마나 흘렀는가"가 곧 "지금이 초반인지 후반인지"를 알려주는 신호로 쓰이는 것입니다.
>
> **`best`(최고기록)와 `cur_obj`(현재 해)를 분리해서 관리하는 이유**: RRT의 정의 자체가 "기록(best) 대비 허용폭"이므로, "지금 당장 들고 있는 해"(`cur_obj`, 다음 파괴의 출발점)와 "지금까지 찾은 최고"(`best`/`best_obj`, 최종적으로 반환할 값)가 서로 다를 수 있습니다 — RRT가 "기록보다 살짝 나쁜 해도 현재 해로 받아준" 경우, `cur_obj`는 나빠져도 `best`는 그대로 최고 기록을 유지합니다. 함수의 최종 반환값이 `state.placements()`(현재 상태)가 아니라 **`best`**인 이유가 여기 있습니다 — 탐색 도중 잠시 나빠졌던 상태로 끝나더라도, 지금까지 찾은 최선의 해를 잃지 않고 반환합니다.

```python
def improve(core, incumbent, budget, *, prob, rng, cfg=None):
    """ALNS 개선 훅. 어떤 예외도 incumbent를 파괴하지 않는다 (설계서 L5)."""
    from solver.alns.loop import improve as alns_improve, AlnsConfig
    improve.last_trace, improve.last_stats = [], {}          # 호출마다 초기화 (stale 방지)
    cfg = cfg or AlnsConfig()
    if not cfg.enabled or not incumbent:
        return incumbent
    trace, stats = [], {}
    try:
        out = alns_improve(core, incumbent, budget, prob=prob, rng=rng,
                           cfg=cfg, trace=trace, stats=stats)
    except Exception:
        return incumbent
    improve.last_trace, improve.last_stats = trace, stats    # solve가 report로 옮김
    return out if out else incumbent
```

`solve(prob_info, timelimit)`의 시그니처를 `solve(prob_info, timelimit, *, alns_cfg=None, report=None)`로 확장하고, 본문의 "멀티스타트 construct 루프" 이후를 다음 흐름으로 수정 (기존 trivial 안전망·최종 utils 검증·전역 try/except 골격은 유지):

```python
def _weighted_obj(core, prob_info):
    """core.objective() 튜플의 가중합. 1주차 shell에 동등 헬퍼가 이미 있으면 그것을 사용."""
    z1, z2, z3 = core.objective()
    w = prob_info.get("weights", {})
    return w.get("w1", 1.0) * z1 + w.get("w2", 1.0) * z2 + w.get("w3", 1.0) * z3
```

> - **`cProfile`**: 프로그램을 실행하면서 "어떤 함수가 몇 번 호출됐고, 그 함수 자체에서(하위 호출 제외) 얼마나 시간을 썼는지, 하위 호출 포함 전체로는 얼마나 걸렸는지"를 자동으로 기록해주는 파이썬 내장 프로파일러입니다. `pr.enable()`~`pr.disable()` 사이에서 실행된 모든 함수 호출이 다 기록됩니다.
> - **`pstats.Stats`**: `cProfile`이 모은 원시 기록을 사람이 다루기 쉬운 형태로 정리해주는 도구입니다. `st.total_tt`(total total time, 전체 실행에 걸린 총 시간), `st.stats`(함수별 상세 통계 딕셔너리)를 여기서 꺼내 씁니다.
> - **`python_share` 함수의 계산**: `st.stats.items()`를 순회하며 "함수 이름에 `ogc_core`가 들어있거나, C 확장 모듈 특유의 표기(`f == "~"`이면서 이름에 `Core`가 있는 경우"를 찾아 그 함수들이 쓴 시간(`tt`)만 따로 합산합니다(`core_tt`). 그러면 `1.0 - core_tt/total`이 "전체 시간 중 C++ 코어가 아닌, 순수 Python 코드가 차지한 비율"이 됩니다. 이게 "Python 전용 시간 비율"의 실제 계산 방법입니다.
>
> **왜 "p50"(중앙값, median)을 쓰는가, 평균이 아니라:** 실행 시간 측정에는 가끔 튀는 값(outlier, 예: 운영체제 스케줄러가 잠깐 다른 프로세스에 CPU를 줘서 유독 오래 걸린 1회)이 섞이기 마련입니다. **평균(mean)은 이런 튀는 값 몇 개에도 크게 흔들리지만, 중앙값(median, 정렬했을 때 정확히 가운데 값)은 훨씬 안정적**입니다. 그래서 성능 벤치마크에서는 관례적으로 "p50"(50번째 백분위수 = 중앙값), 필요하면 "p99"(꼬리 지연시간 확인용) 같은 백분위수 지표를 씁니다. `statistics.median()`이 파이썬 표준 라이브러리로 이를 바로 계산해줍니다.
>
> **`bench_iteration`이 "`state.restore(snap)`을 매회 호출"하는 이유**: 매 반복마다 "제거 33개 → 복구 시도"를 하고 나서, **결과가 성공이든 실패든 무조건 원래 상태로 되돌립니다.** 이렇게 해야 매번 "같은 조건(같은 배치 상태)에서 시작하는 반복"을 여러 번 측정할 수 있어, 측정값들 사이에 비교 가능성이 생깁니다(측정할 때마다 상태가 계속 달라지면 "느려진 게 연산자 때문인지 상태가 우연히 어려워져서인지" 구분이 안 됨) — 성능 측정을 위한 "통제된 실험" 설계입니다.
>
> **"30% 규칙"(결정 규칙)이 의미하는 것**: `verdicts["port_repair_to_cpp"]`가 "Python 전용 시간이 30%를 넘으면 True"로 계산됩니다. 이건 **"측정도 안 해보고 성급하게 C++로 이관하지 말라"**는 원칙의 실천입니다 — 실제로 시간을 재봤더니 이미 대부분(70%+)의 시간이 C++ 코어 안에서 쓰이고 있다면, Python 쪽을 아무리 최적화해도 전체 속도에는 큰 영향이 없으므로 이관할 가치가 없습니다. 반대로 Python 쪽이 30%를 넘게 차지한다면, 그 부분을 C++로 옮기는 게 실질적인 속도 향상으로 이어질 만한 근거가 됩니다.
```python
"""construct vs alns 결과 JSON 비교표 + 완료 기준 판정."""
import json, sys

def main(construct_path, alns_path):
    c = json.load(open(construct_path))["results"]
    a = json.load(open(alns_path))["results"]
    names = sorted(c, key=lambda n: int(n.split("_")[1]))
    sum_z1_c = sum_z1_a = 0.0
    feas_c = feas_a = 0
    print(f"{'inst':>8} {'Z1(con)':>10} {'Z1(alns)':>10} {'ΔZ1%':>7} {'obj(con)':>12} {'obj(alns)':>12}")
    for n in names:
        rc, ra = c[n], a[n]
        feas_c += bool(rc["feasible"]); feas_a += bool(ra["feasible"])
        sum_z1_c += rc["obj1"]; sum_z1_a += ra["obj1"]
        dz = 100.0 * (rc["obj1"] - ra["obj1"]) / rc["obj1"] if rc["obj1"] else 0.0
        print(f"{n:>8} {rc['obj1']:>10.1f} {ra['obj1']:>10.1f} {dz:>6.1f}% "
              f"{rc['obj']:>12.0f} {ra['obj']:>12.0f}")
    red = 100.0 * (sum_z1_c - sum_z1_a) / sum_z1_c if sum_z1_c else 0.0
    print(f"\nfeasible: construct {feas_c}/{len(names)}, alns {feas_a}/{len(names)}")
    print(f"sum Z1: {sum_z1_c:.1f} -> {sum_z1_a:.1f} ({red:.1f}% 감소, 목표 >= 20%)")
    ok = feas_c == len(names) == feas_a and red >= 20.0
    print("EXIT CRITERIA:", "PASS" if ok else "FAIL")
    return 0 if ok else 1

if __name__ == "__main__":
    sys.exit(main(sys.argv[1], sys.argv[2]))
```

## 계약 변경 요청

1주차 계약(Core API·solver 모듈 시그니처)은 본 계획에서 **일절 수정하지 않는다**. 다만 아래 4건은 1주차 문서에 명시된 지점의 확장이므로 승인 후 1주차 계획서의 계약 절에도 동기화할 것.

1. **`shell.improve` 훅 키워드 인자 추가 (필수)** — 1주차: `improve(core, incumbent, budget)` pass-through. 요청: `improve(core, incumbent, budget, *, prob, rng, cfg=None) -> Placements`. 근거: Shaw 관련도(shape bbox), Z2 델타(workload), Z3(pref), 목적 가중치(w1/w2/w3)는 `prob_info`에만 있고 Core 계약에 노출되지 않음. 위치 인자 3개는 유지되므로 기존 문구와 충돌 없음. 호출자는 shell.solve 하나뿐.
2. **`shell.solve` 키워드 전용 인자 추가 (필수)** — `solve(prob_info, timelimit, *, alns_cfg=None, report=None)`. 근거: 벤치 ablation(--disable-op)과 수렴 trace 수집이 제출 경로(`myalgorithm.algorithm`은 여전히 `solve(prob_info, timelimit)` 위치 인자만 사용)와 분리된 채로 필요. 기본값이 None이라 1주차 호출부·테스트는 무변경.
3. **`ogc_core` 테스트 전용 바인딩 추가 (고지)** — `_nfp_bitmap(bi, oi, bj, oj, kind, method) -> (dx_lo, dy_lo, w, h, bytes)`. 1주차 `_overlap`/`_static_bit` 선례를 따르는 비계약(언더스코어) 바인딩으로, 공개 Core API 불변. 승인 불요라 판단하나 투명성 위해 기재.
4. **`Core.best_insertion` 추가 (조건부 — Task 11 결정 대기)** — Task 11 측정에서 Python 전용 시간 > 30%일 때만: `best_insertion(block, t_max) -> tuple[bay, x, y, orient, entry] | None` (전 bay×방향의 최소 (지각, y, x) 후보를 C++에서 일괄 탐색). 설계서 §4 L1의 "best_insertion — 디코더 내장 루프" 항목을 계약으로 승격하는 것. 트리거되지 않으면 요청 철회.

> 💡 **설명 — 이 절은 1주차 주석본에서 본 "계약 부록"과 정확히 같은 성격의 "프로젝트 관리" 절입니다.** 1주차 계획은 이미 확정되어 3~4주차가 그 위에 의존하고 있으므로, 2주차 작업 중 "1주차 계약을 살짝 넓혀야 할 필요"가 생기면 **마음대로 바꾸지 않고 이렇게 명시적으로 "요청" 형태로 기록**해 승인 절차를 거칩니다(실제로 1주차 주석본에서 본 "계약 부록"이 이런 요청들을 취합해 최종 확정한 결과물이었습니다). 눈여겨볼 것은 요청 4번 — "조건부"라는 표현대로, **Task 11에서 실측한 결과(30% 규칙)가 조건을 충족할 때만 발동**하고, 그렇지 않으면 "요청 철회"라고 스스로 명시해뒀습니다. 이는 "필요한지 확인도 안 하고 미리 API부터 넓혀놓는" 과잉 설계(YAGNI 원칙 위반)를 피하려는 신중한 태도입니다.
